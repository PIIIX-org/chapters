# Unit 3 — Admin and the onboarding path

Implements the unit 3 section of
`docs/superpowers/specs/2026-08-22-remaining-ui-design.md` against
`docs/superpowers/specs/2026-07-15-admin-oversight-dashboard-design.md`.

## Why this unit is third

Signup sets neither `status: 'active'` nor `emailVerifiedAt`, and login
(`auth/routes.ts:169`) requires both. Approval has no UI, so until this ships
nobody but the bootstrap admin can get into the instance.

## Load-bearing rules

- **Metadata only, never content.** No view here shows note text, frontmatter
  values or revision bodies. The audit trail shows *who changed which path
  when*, not what changed.
- **Login stays generic.** An unapproved user keeps seeing
  `invalid credentials` — saying "pending approval" there leaks account
  existence. The waiting state is stated on signup and verify-email, where
  the visitor already proved they own the address.
- Force-revoke is structural: it removes access, never grants read.

## Backend gaps found (the spec's addition table lists none for this unit)

| # | Gap | Why it blocks the unit |
|---|---|---|
| 1 | No instance-wide MCP connection list | `POST /admin/mcp-connections/:id/revoke` exists but an admin has no way to see an id to revoke |
| 2 | `GET /admin/users` omits `emailVerifiedAt` | Login needs approval **and** verification; approving an unverified user leaves them locked out with nothing on screen explaining why |

Both are additive selects on existing admin routes. No new tables, no new
permission surface.

## Tasks

1. Backend: `GET /api/admin/mcp-connections` (metadata only — never
   `tokenHash`), `emailVerifiedAt` on `GET /api/admin/users`. Integration
   tests in `server/test/admin-dashboard.test.ts`.
2. Client `api/admin.ts` + `hooks/useAdmin.ts` over every admin endpoint.
3. `/admin` route, admin-only guard, page shell with section nav.
4. Approval queue + user management (approve / deactivate / promote /
   transfer vault ownership), each with inline consequence copy.
5. Oversight tables: vaults, teams, shares (force-revoke), MCP connections
   (force-revoke). Share rows are joined to names client-side from the vault,
   user and team lists — no UUIDs on screen, no new endpoint.
6. Instance activity: security events + audit trail (both paginated),
   aggregate stats, instance backup download.
7. Onboarding copy on the signup screen. Login error untouched.
8. ⌘K "Go to admin", admins only; drop the now-stale "do not add admin
   commands" comment in `SearchOverlay.tsx`.
9. README + STATE.md.

## Testing

Client: vitest + happy-dom in the existing style, an axe assertion per new
component. Every test mutation-verified — the "test that cannot fail" has
appeared seven times in this repo, always a fixture too uniform to tell
working from broken. Fixtures here carry a mixed roster (verified and
unverified pending users, an admin and a member, a revoked and a live MCP
connection) so a missing gate cannot pass.

Server: real-database integration tests, including a non-admin 403 on both
new reads.
