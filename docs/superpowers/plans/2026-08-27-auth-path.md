# The sign-in path

Closing the dead ends between the six auth pages, and making the route from
stranger to signed-in visible while someone is walking it.

## What is actually broken

All six auth pages exist and work in isolation. **There is not one `<Link>`
between any of them.** They are islands reachable only by typing a URL:

| From | Missing | Consequence |
|---|---|---|
| `/login` | → `/signup` | **A new person cannot reach sign-up at all.** |
| `/signup` | → `/login` | Someone who already has an account is stuck. |
| `/verify-email` | → `/login` | Verifies, then has nowhere to go. |
| `/forgot-password` | → `/login` | No way back. |

The two links that do exist (`login → forgot-password`, `setup → login`) are
raw `<a href>`, so they hard-reload the SPA instead of routing.

Every browser pass passed because nobody ever walked in as a stranger. This is
the third instance of one class: vault creation (unit 1) and connect-repository
(unit 7) were the first two — a surface only reachable from a place you can
only get to if you already have the thing it creates.

## The four states, and the one nobody can act on

Signup sets `status: 'pending_approval'` with no `emailVerifiedAt`. Login
(`auth/routes.ts:169`) requires **both** to be settled. So:

1. **Create account** — signup, code mailed.
2. **Confirm your email** — enter the code; `emailVerifiedAt` set.
3. **Admin approval** — the person can do nothing here, and login deliberately
   refuses to say anything (see below).
4. **Sign in.**

Step 3 is the whole problem. The good news is that it ends by itself: the
approve handler calls `notify()`, which writes the in-app row **and emails the
person**. So "we'll email you when an admin approves" is a true promise, not a
hopeful one — provided SMTP is configured, which is already the first item on
the deploy checklist.

## Load-bearing: the login error stays generic

Unit 3 settled this and `STATE.md` records it. An unapproved user gets
`invalid credentials`, because saying "pending approval" there confirms to a
stranger that an address has an account on this instance. The waiting state is
explained on signup and verify-email, where the visitor supplied the address
themselves and there is nothing to leak. **Do not "improve" the login error.**

## Tasks

1. `components/auth/AuthSteps.tsx` — the four steps, current one marked.
   Rendered on the signup journey (signup, verify-email) so the whole path is
   visible from the first screen. **Not on `/login`**: that is the everyday
   sign-in page and a returning user does not need a 4-step onboarding every
   morning.
2. Links closing all four dead ends above, and the two `<a href>` converted to
   `<Link>`.
3. The post-verify screen becomes a real step 3: verified, an admin has to
   approve, we will email you, and here is where to sign in when we do. Today
   it verifies and then just sits there.
4. README + STATE.md.

## Testing

mutation-verified**. Then the browser pass that would have caught this:
walk in as a stranger with no URL bar — land on `/login`, find sign-up, get
through verification, and read what to do next.
