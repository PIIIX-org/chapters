## Verified
- **Block ids**
  - The key is `sha256(file id ␟ kind ␟ inner_path ␟ sibling_index)`. Same content gives the same id.
  - A line shift or an edit elsewhere keeps both the `b_…` id and the row uuid (the upsert); tests cover this.
  - A block moved inside its file keeps its id. Moving it to another class or another file, renaming the symbol, or renaming the file gives a new id; the file id is stable because `syncRepositoryFiles` updates the row in place.
  - Inserting a same-named overload earlier in the file shifts the sibling indexes, so ids swap. That follows from the formula.
- **Line contract**: ranges are 1-based and inclusive everywhere.
  - `totalLines` gives the same counts as the old `countLines` in `read_file` paging.
  - `find_symbols` uses the tree-sitter row + 1.
  - Graph evidence and #942 edge rows are `path#La-Lb` via `mcp/response.ts` `location`; the import line is 1-based.
  - The SQL snippet (`string_to_array(..)[a:b]`) matches `sliceLines`.
- **Migration 0035**
  - Journal idx 35, `when` 1792150000000, after 0034's 1792100000000. Dev is at 0032; the only other open PR with a 0035 file is #985, which is stacked on this one.

## Findings (blocking)
1. **The lab is red because of this PR: 2 regressions** (`lab/lib/fixlab.ts:196`).
   - Run 40064498867, checks "filesPendingExtraction reaches 0" in `fix-crash-catchup` and `zz-fix-minified-bundle`: "SQL pending -1".
   - `sqlPending` still queries `repository_files … embedding is null`, and `server/drizzle/0035_blocks.sql:69` drops that column, so psql fails and the helper reads -1.
   - Fix: count files with no current block, i.e. `NOT EXISTS (SELECT 1 FROM blocks b WHERE b.owner_type='code' AND b.owner_id=f.id AND b.owner_version=f.content_hash AND b.embedding IS NOT NULL)`. Then attach a green lab run.
2. **`find_symbols` and `search` scan every file's content on each query** (`server/src/search/search.ts:215-217`, and `:95-97`).
   - The keyword symbol leg now runs `content ILIKE '%q%'` over every `repository_files` row in scope, with no trigram index. It then splits each matching file into lines, and splits `f.content` again for every hit's snippet.
   - Measured on the same 768-file corpus, keyword leg alone: base 5–6 ms; head 47 ms for `processFile` and 109 ms for `x`.
   - End to end, `find_symbols` went from 8–10 ms to 41–132 ms. This explains the bench's msMedian going from 42 to 116 ms.
   - The cost grows with the repository's total bytes.
   - Fix: store the snippet on the block row, as `repository_file_symbols.snippet` was before, and match and return it from there.
3. **The outline comes back out of line order after a re-extraction** (`server/src/repositories/store.ts:169-181`).
   - `listFileSymbols` has no `ORDER BY`, and the upsert moves rows around in the heap. The REST file view and the client `SymbolOutline` show them as returned.
   - Reproduced on a `blocks` table with free space: after adding `first()` at the top, the outline is `["beta@9","first@1","alpha@5","gamma@13"]`.
   - The PR's own test failed this way in my 12-file run (`['beta','alpha','delta']`) and passes when the file runs alone.
   - Fix: `.orderBy(asc(blocks.startLine), asc(blocks.blockId))`.
4. **`Closes #413` and `Closes #460` would close issues whose ask is not met.**

   - Fix: change both to `Refs #413` and `Refs #460`, and keep `Closes #418`.
