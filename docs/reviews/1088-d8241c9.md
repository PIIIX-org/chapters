# Review of PIIIX-org/chapters#1088 — feat: a vault is a read-only git remote: clone and pull its notes (#677)
Head reviewed: ce08e5ddc31d770894331d3312c67e16e8c86e08

No pre-review comment was posted on this PR.

## Scope checked
- Everything in the diff: `git-remote/routes.ts`, `git-remote/vault-remote.ts`, the `app.ts` mount, the `index.ts` sweep, both access matrices, `vault-git-remote.test.ts`, `backup.md`, `backend-reference.md`, and both `mcp-tools.md` manuals.
- Consumers outside the diff: `resolveMcpToken`, `resolveAccess`, `checkRateLimit`, `resolveNotePath` (note paths), `purgeRevision` and `purgeNote`, and the `mcp_connections` columns including `profile`.
- I checked out the head and ran it against my own Postgres on port 5488 and my own TMPDIR. All of it is now removed.

## Verified
- **Real git works.** `server/test/vault-git-remote.test.ts` passes 7/7. It runs real `git clone`, `pull` and `grep` against a live `listen()`ed server. A pull after an edit moves HEAD, a pull after a soft delete drops the file, and `git push` fails.
- **Matrix passes.** `access-matrix.test.ts -t "git clone"` passes 4/4: owner, shared, revoked and unrelated, with no identifier in any denied answer. The entry is present in both `server/test/access-matrix.test.ts` and `lab/tests/access-matrix.test.ts`.
- **Auth on every request.** `info/refs` and the POST both go through `authorise`, so a clone after a share revoke gets 404.
  - The token is resolved live: a revoked or expired token, or a non-active owner, gives 401.
  - A repository-pinned token, a vault pin to another vault, an allow-list without `read_note`, a missing vault, a malformed UUID and no access all give the same 404.
  - `receive-pack` returns 403 only after authorisation. There is no `git-receive-pack` POST route, so nothing can be pushed.
- **No path traversal.** The directory name comes from a UUID that is regex-checked before use. Note paths are slug-only, with no `.`, `..` or hidden segments, and at most 8 segments (`okf/paths.ts`).
- **Trashed notes excluded.** The build uses `deleted_at is null`.
- **Credentials.** They are not logged: auth failures log a `mcp_auth_failed` event with only the IP.
- **Protocol.** It runs `git upload-pack --stateless-rpc` in protocol v0 and ignores `Git-Protocol`. The git 2.50 client works with that.
- **Manuals and tools.** The two `mcp-tools.md` manuals are byte-identical (same blob hash). No tool definition changed. `mcp-manuals` and `mcp-tool-budget` pass 10/10.
- **Migrations.** None were added.

## Findings (blocking)
1. **P1 — `server/src/git-remote/vault-remote.ts:59-90`: history keeps purged and replaced content, and serves it to every reader.**
   - Each change appends a commit on top of the old head and nothing is ever pruned.
   - `purgeRevision` exists for accidentally committed secrets (`notes/store.ts:2155`, "where recoverable is the wrong property"). `purgeNote` and soft delete also remove content. None of them touches `DATA_DIR/git-remotes`.
   - I reproduced it. I cloned, set a note body to `password=SECRET123`, pulled, then edited the note to `cleaned` and pulled again. `git log -p` on the clone still shows `-password=SECRET123` and the original body. The same holds for a trashed note's earlier commits.
   - The remote therefore keeps content that the owner deliberately and irrecoverably removed, for as long as the vault exists.
   - Fix options: build a single-commit snapshot with no history. A rebuild would then still be a non-fast-forward for every client, which is why it is tied to finding 3. Or rewrite or drop the repository when `purgeRevision` or `purgeNote` runs. The latter needs a purge hook, so it is not a small change.
2. **P2 — `server/src/git-remote/routes.ts:86`: unbounded gzip inflate.**
   - `gunzipSync(raw)` has no `maxOutputLength`.
   - A 917 KB gzip body of zeros, sent with a read token, was inflated to a 900 MB buffer on the event loop and handed to git. It returned 500 only after the 900 MB was allocated.
   - Any read token can do this repeatedly. A cap of a few MB, for a request that is only `want`/`have` lines, fixes it.
3. **P2 — `vault-remote.ts:59-90`: history is not derivable from the database, so the cache is not safe to delete.**
   - Commits are one per fetch that saw a change, and the parent is whatever the previous head was.
   - `backup.md` and the backend-reference say the directory is "derived… safe to leave out". After a restore, a lost volume or the sweep, the rebuilt repository has an unrelated root commit.
   - Every existing clone's `git pull` then fails with "refusing to merge unrelated histories" or diverges.
   - Either document that loss breaks existing clones (the 'cache' wording is wrong), or make the history deterministic from the database. Dropping history, as in finding 1's first option, would also remove the client-side surprise.
4. **P2 — `vault-remote.ts:78`: `Math.max(0, ...rows.map(...))` overflows the stack.**
   - Between 100k and 200k live notes it throws `RangeError: Maximum call stack size exceeded`. I ran this under Node: 100k args works, 200k fails.
   - The build then throws on every request, so the vault can never be cloned.
   - Use `rows.reduce` instead.

## Minor
- **Resource cost.** Each of the two requests in a clone calls `build()`, which selects every live note including all bodies, renders them and hashes them, before the one `git log`. The "an unchanged vault costs one query" doc line is true in query count only. The cost is O(vault size) per request. Builds for one vault serialise in-process, and the rate limit is 120 per connection per minute. A cheap pre-check such as `count`, `max(updated_at)` and `sum(hash)` in SQL would avoid loading bodies.
- No `git gc` or repack. Each rebuild is a `fast-import` run, so packs accumulate. `checklist.md` §6 has a disk-budget entry for git-mirrors but none for git-remotes.
- Fixed commit author `Elara <elara@localhost>`; harmless.
- If the newest note is removed, the commit date goes backwards.
- Tests: `vault-git-remote.test.ts` has no gzip-encoded negotiation test, no rate-limit test and no assertion about history content. The matrix covers shared and revoked.
- **Parallel-edit race — not exercised.** I did not exercise an edit landing between the `info/refs` and POST requests. I expect `upload-pack` to accept an old tip that is still an ancestor, but I did not run it.

Budget delta: reader +0 tokens, writer +0 tokens (no tool definition or description changed; only the manual text in `skills/*/references/mcp-tools.md` is touched, and `mcp-tool-budget` and `mcp-manuals` pass).

Verdict: CHANGES

   - The repository holds two commits: a fixed empty root and one snapshot child, rewritten with `fast-import --force`. It then runs `reflog expire --expire=now --all` and `gc --prune=now`.
   - Reproduction: I set the body to `password=SECRET123`, cloned, updated the note to `cleaned`, then ran fetch and `reset --hard origin/main`.

   - Unchanged vaults keep the same commit, so `git pull` is a no-op for them.
   - The stable empty root makes `pull --rebase` work for an unmodified clone. That is tested, as is a plain `pull --ff-only` refusing.
2. **gzip inflate cap: resolved.**
   - `gunzipSync` uses `maxOutputLength` of 1 MiB, and the POST has a 1 MiB `bodyLimit`.
   - A 1 MiB + 1 byte zero gzip returns 413, and the test's 64 MiB bomb returns 413 without being inflated.
3. **Rebuild after cache loss: resolved, documented.**
   - A rebuild gives the same root id, and the snapshot commit is deterministic from the content: fixed author, newest `updated_at` as date, same tree. If the repository is lost and rebuilt, clients update with `git pull --rebase`, or with `fetch` and `reset`. This is documented in `docs/agents/backend-reference.md` and `docs/self-hosting/backup.md`.
4. **`Math.max(...spread)`: resolved.** The newest date is now a `reduce` (`vault-remote.ts`). No spreads remain in the diff.

None.

## Minor

A 1,000,000-byte zero gzip and exactly 1 MiB of zeros both returned 500, not 4xx. Memory is bounded, so this is not a DoS. Catching a non-zero upload-pack exit and returning 400 would match your "expect 4xx" wording.
- A clone running during a rebuild's `gc --prune=now` can fail once and need a retry. This is documented and accepted.
- Builds are serialised per process only. This is fine for a single-node deployment.
