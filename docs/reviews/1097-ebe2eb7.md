## Verified
- **No production TRUNCATE.** A grep of `server/src` finds no `truncate` statement. The TRUNCATE in #1094's error is only `wipeInstance` in `server/test/helpers.ts`, which locks every table AccessExclusive one by one.
- **Restore cannot deadlock with extraction.** `applyRestore` (`export/restore.ts:573`) runs one transaction of `INSERT … ON CONFLICT DO NOTHING`, and restore runs on an empty instance only. It takes no `FOR UPDATE`, advisory or table lock, and it does not kick extraction or the semantic-edge worker.
- **The test leaves extraction in flight.** `backup-roundtrip.test.ts:596-611` syncs files and then calls `wipeInstance()` at line 603 and in the final cleanup, never flushing extraction. The helper comment "No caller syncs repository files" was already stale. `flushExtraction` exists at `extraction-queue.ts:321` and `flushExtraction` is already imported by `access-matrix.test.ts` and `blocks-code.test.ts`. Calling it first is right, because the extraction job awaits its own `runSemanticEdgeRefresh` inline (`extraction-queue.ts:700`), so nothing it queues is left behind.
- **No production cycle from #1077's change recording.** I read the lock order in `repositories/store.ts` and `extraction-queue.ts:660-700`:
  - Per-file change transaction: it updates the file row, then writes `repository_changes`.
  - Finalizing transaction: `repositories` row `FOR UPDATE`, then updates `repositories` and writes `repository_versions` and `repository_changes`. It never touches file rows or the advisory lock.
  - Extraction transaction: advisory `code_edges:<repo>` lock first, then the file row `FOR UPDATE`, then imports, blocks and edges.
  - The finalizer waits only on holders of the repo row's FK `KEY SHARE`. Extraction takes the advisory lock and the file lock first, so I see no cycle among these three.
  - `store.ts:179` already takes the advisory lock first, the same order extraction uses.
- **Conclusion: test cross-talk, not a production deadlock.** The PR's claim, "No production lock order is involved", holds up on this read. The cause is a background extraction job from the previous step racing the helper's TRUNCATE, and it is fixed at the cause with no retry or weakened assertion.
