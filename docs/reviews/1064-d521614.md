## Verified
- **exact@1 definition.** `exactAtK` counts a result when it has lines and shares a path and at least one line with a gold range. Results with no lines never count. This matches the gold `{path,start,end}` format.
  - This is overlap, not the issue's "covers". The PR states the choice.
  - Hits with a range are mostly symbol spans, so a large enclosing symbol counts as exact@1.
  - Results from an `ambiguous` answer still count toward `exact1`, because `hits` is not cleared when `abstained` is set.
- **goldReachedRate.** It is `tokensToGold !== null` over questions, computed per suite. `abstained` is computed. `exact1`, `exact5`, `goldReachedRate` and `abstained` are in `METRICS`, so `toBaseline` records them.
- **Old baseline.** A reference without the new fields does not judge them: `vsRef` is `'same'` and the "baseline lowered" rule skips them. The run is "stale" until the baseline is recorded. This is tested.
- **Gate tolerance.** Exact@1 and goldReachedRate use the same rule as `hit5`: more than one question lost is red.
- **Paired ratio.** The ratio and the not-exact table are rendered in the gate summary (seen in the run output).
- **Grep side.** `runGrep` is unchanged apart from the new return fields. The Elara span window is 10 lines before and 30 after the hit range, the same constants (`GREP.readBefore` and `readAfter`) the grep agent uses. The window comes from the hit's location, not from gold.
- **Exit-criteria text.** Added to the README and `docs/agents/github-workflow.md`.
- **CI.** `fails-before`, `checks` and `plan` pass on the head. The plan has `bench-suite-change` set. The head's 3-instance bench is still running (started 11:56Z; the previous run took about 1h50).
