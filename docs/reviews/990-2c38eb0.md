## Findings (blocking)

**1. Bump the `vitest` override to match the new `^5.0.5` range. P1, confidence 0.97**
- **Where:** `client/package.json:59`, `server/package.json:61`, and `pnpm-workspace.yaml:31`, which is outside the diff.
- **Cause:** both manifests now say `"vitest": "^5.0.5"`, but `pnpm-workspace.yaml` still overrides `vitest: ^5.0.3`. The lockfile therefore records `specifier: ^5.0.3` for both projects. Frozen installs pass, but pnpm's pre-run dependency check finds the manifests and lockfile out of step.
- **Effect on CI:** `offline-scripts` fails at its "pnpm dependency check on its own" step with `[ERR_PNPM_VERIFY_DEPS_BEFORE_RUN] The lockfile in /app does not satisfy project of id client`. The Dockerfile comment describes this exact failure for the earlier `adm-zip` case.
- **Effect locally:** with the default setting, every `pnpm <script>` now runs a full workspace install first once a manifest is newer than the last install.
- **Reproduced:** touching the three manifests and running `pnpm_config_verify_deps_before_run=error pnpm -C server check-notes --help` gives the same error.
- **Fix, tested:** set the override to `vitest: ^5.0.5` and run `pnpm install --no-frozen-lockfile`. The lockfile diff is 5 lines (the overrides entry, two importer specifiers, two peer specifiers). After that the check prints `usage: check-notes …` and a frozen install is still clean.
- **Process gap:** Dependabot will hit this again every time it bumps vitest, until the override and the manifests stay in step.

**2. Stop editors from removing agent presence now that hocuspocus applies removals. P2, confidence 0.85**
- **Where:** `server/package.json:26`; the fix goes in `server/src/sync/collab-server.ts:550` and `agent-presence.ts`.
- **What changed upstream:** 4.7.1 (#1162) applies awareness removals again. Removals no longer appear in `states`; they arrive in a separate `removedClients` set that hooks must filter.
- **Our gap:** `beforeHandleAwareness` calls `stripAgentClaims(documentName, states)`, which promises that "a state aimed at an agent's client id (to replace or remove it) is dropped". It only filters `states`, so a removal of the agent's client id from any editor's connection now reaches every client. The trigger can be a crafted update, or the removal y-protocols issues when a remote state times out, which the provider forwards because it only skips its own changes.
- **Proof:** I wrote a scratch test (two people, an MCP edit, then one client removes the agent's id with origin `'timeout'`). On 4.7.0 the watcher still sees the agent and the test passes. On 4.7.1 the watcher sees 0 agents and the test fails.
- **Impact:** the presence is hidden until the next 15 s renewal; repeated removals hide it for good. This breaks #481's rule that a client speaks only for itself.
- **Fix:** destructure `removedClients` in the hook, pass it to `stripAgentClaims`, and have it run `removedClients.delete(id)` for every agent client id. A regression test like the scratch one should come with it.
