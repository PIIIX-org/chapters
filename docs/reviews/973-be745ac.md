## Minor
- **Search and graph disagree within a millisecond.** The SQL legs compare `updated_at` (microseconds) against a millisecond bound, while `passesFilters` compares the millisecond-truncated text. I probed a note with `updated_at = 2020-01-01T00:00:00.000500Z`:
  - `until=2020-01-01T00:00:00.000Z` (and `until=2020-01-01`): search says `no_match`, the graph includes the note.
  - So a hit's own `updatedAt` passed back as `until` drops that note from search but keeps it in the graph.
  - **Fix:** `date_trunc('milliseconds', updated_at) ${op} ${bound}::timestamptz` in `updatedBound`.
- **Dates outside years 0000–9999.** `timeBound` passes them through, which contradicts the PR's "a bound that is no date matches nothing":
  - `since=+010000-01-01T00:00:00Z` and `since=-000001-01-01T00:00:00Z` make the Postgres cast fail on both legs. Search answers `200 {"status":"unavailable","degraded":{"reason":"vector_leg_failed"}}` and logs errors for both channels.
  - In the graph, the `'+010000…'` string sorts before `'2020…'`, so `since` year 10000 keeps every node.
  - **Fix:** in `timeBound`, return null unless the ISO string matches `/^\d{4}-/`.
- **A bound without an offset uses the server's time zone.** `Date.parse` reads `2026-10-24T10:00` in the process's local time zone. The docs don't say so, and should say a bound needs an offset or is read in the server's zone.
- **A date-only `until` excludes that day.** A date-only `until` (what the graph's `<input type="date">` sends) means 00:00Z of that day, so "until today" excludes today's edits. The old string comparison behaved the same way, so this isn't a regression, but the PR is a natural place to treat a date-only `until` as the end of the day.
- **The client mock still filters on `timestamp`.** `client/mock/server.mjs:1321` filters the graph on `n.timestamp ?? n.updatedAt`, and its search hits have no `updatedAt`. It is now out of step with the server.
