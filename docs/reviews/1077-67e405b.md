## Scope checked
- **New surface:** an extra `changed_since` param on the existing `browse_repository` MCP tool. There is no new tool and no REST route.
- **Code:** `repositories/changes.ts`, `mcp/changes.ts`, the `store.ts` recording, migration 0063, schema, both manuals and both matrices.
- **Callers of `syncRepositoryFiles`:** git sync, the scheduler and the push route.
- **Backup:** `backup-format.ts`.

## Verified
- **How "since a commit" is computed:**
  - It does not use git or the mirror. It reads the index's own history: `repository_versions` and `repository_changes`, recorded in `syncRepositoryFiles` from content-hash diffs.
  - A depth-1 mirror therefore cannot cause a wrong answer.
  - A commit the index never recorded returns `INVALID_ARGUMENT` ("commit not in the index history"). It does not return a wrong list.
  - A commit prefix that matches two different commits is refused as ambiguous.
  - Rewritten history is harmless: only the commits that were actually synced are known.
  - SHA-256 works: the regex accepts 7–64 hex characters, and the push route accepts 40- or 64-character commits.
- **Folding per path:** the added/modified/deleted rules are correct. Added-then-deleted drops out, and deleted-then-added becomes modified.
- **Access:**
  - `requireRepositoryAccess` runs before anything else.
  - The test asserts that an account without access gets the same refusal text as the plain listing.
  - Matrix entries exist in both `server/test/access-matrix.test.ts` and `lab/tests/access-matrix.test.ts`.
  - Folder filtering is range-based (`>= folder/`, `< folder0`), not `LIKE`, so a folder name cannot act as a wildcard.
  - I found no path leak after a revoke.
- **Bounds:** a keyset page of 500 with a cursor, `truncated`, and a token-budget ladder. A 620-file paging test covers it.
- **Manuals:** both `skills/*/references/mcp-tools.md` files are byte-identical. The new param is described.
- **Migration:** numbered 0063 at 1793750000000, with a journal entry.
- **Budget (from the PR body):** the reader profile sits at 2000 tokens, which is within the cap but leaves zero headroom. I did not measure it.
- **Fails-before:** the new case in `repository-indexed-version.test.ts` uses a param that dev does not have. The CI `fails-before` job passed.

## Findings (blocking)
1. **`server/src/repositories/changes.ts:36-44,57` — a date before the first version silently omits every baseline file.**
   - The baseline version records no changes. For a date older than all versions, `base` is null and the query returns only changes after the baseline, with no `since` in the head.
   - On a repository that has been synced once, `changed_since: '2000-01-01'` returns an empty list. On a repository synced several times it returns a partial list.
   - A caller reading "everything changed since 2000" gets a false "nothing" or "only these". The test at `repository-changed-since.test.ts:122` locks this in as intended.
   - Fix: when `base` is null, say so explicitly (for example `since: null` with a note that the history starts at the baseline), or list the baseline files as `added`. Do not return a bare partial list.
2. **`server/src/export/backup-format.ts:106-120` — backup restore leaves `version_seq` set but restores no version rows.**
   - `repository_versions` and `repository_changes` are not in `BACKUP_TABLES`, and `onRestore` nulls `lastSyncedCommit` and `treeHash` but not `versionSeq`. This is from reading the code; I did not run a restore.
   - A restored repository therefore has `version_seq = N > 0`, no versions, and an empty file index.
   - The next sync takes the `before.seq > 0` branch, so every file is recorded as an `added` change in version N+1, not as a baseline.
   - `changed_since` on a date then lists the whole repository as "added". Commits from before the backup are unknown.
   - Fix: reset `versionSeq: 0` in `onRestore`, and add a backup round-trip assertion.
3. **`server/src/repositories/changes.ts:40` — a date-time without an offset is parsed in the server's local time.**
   - The regex accepts `2026-10-31T12:00` with no `Z` or offset, and `new Date()` reads that as local time. Date-only values are UTC.
   - The answer therefore depends on the server's `TZ`, which neither the param description nor the manual states.
   - Fix: reject a date-time without an offset, or append `Z`, and document that dates are UTC.
4. **`server/src/repositories/store.ts:~125-205` — a failed sync can drop its changes from the history permanently.**
   - File inserts, updates and deletes happen per file, outside the transaction that records the version.
   - If the process dies or throws after the file writes and before that final transaction, the next sync sees identical content hashes and records nothing. Those changes never appear in `changed_since`.
   - The tree hash heals itself on the next sync; the change list does not.
   - Fix: record the changes within the same transaction as the writes, or derive a missed delta on the next sync.

## Minor
- The reader profile is exactly 2000 tokens, so any next addition to `browse_repository` or another reader tool breaks the budget. The PR trimmed three unrelated reader tool descriptions (`find_symbols`, graph, shortest path) to make room, which removes guidance from them.
- `repository_changes` grows without limit (no pruning). On a repository's first sync after a backup restore, every file gets a row.
- In the fails-before case, dev most likely fails on an unknown-argument error from `callText` rather than on an `expect` assertion. Worth confirming against the base run. The other new test file fails on base at import.
- The lab matrix entry has not been run locally. Its `lab` job and `bench (1–3)` were still pending when I checked.

The round-trip test builds a backup at `versionSeq` 2, wipes and restores it. It then asserts `versionSeq` is 0 and both tables are empty. A sync after the restore records version 1 with no changes, so nothing is listed as "added". `onRestore` is documented.
3. **Date-time without offset — resolved (treated as UTC).** The shape regex accepts an optional offset. A bare time gets `Z` appended, so the server's TZ is irrelevant. It is documented in the manual. The test compares `hourAgo` with `hourAgo` + `Z` and expects identical `since`, resolving to C2. Junk input gets `INVALID_ARGUMENT` naming the accepted forms.
4. **Non-atomic history — resolved.**
   - Each file's write and its `recordChange` share one `db.transaction`. Deletions are recorded inside the existing delete transaction.
   - Changes go under `pendingSeq = version_seq + 1`. The finalizing transaction takes `FOR UPDATE` on the repositories row, counts the changes at that seq, and records a version if there are any or the commit changed. A sync that stops midway therefore leaves its rows for the next sync to pick up.
   - Within one version, added→deleted nets to nothing, and deleted→added becomes modified.
   - The test `a sync that stops midway…` uses a throwing getter on the third file. After the retry it expects w added, x modified, z added.
   - Retention is 200 versions, with the version and change rows pruned together (tested).
