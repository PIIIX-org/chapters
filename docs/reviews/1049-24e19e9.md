- #1046 is a thorough PR with Problem, Change, Evidence, benchmark and failing-test sections, yet it fails.
- Wider sample: I ran every merged PR whose body contains a closing keyword among the last 80 merged to `dev`. That gave 44 PRs.
  - 31 of the 44 (70%) FAIL on the first pass.
  - 12 of the 44 close issues with no acceptance items, so the check does nothing for them.
  - Of the 32 that have items, 31 fail.
  - 115 of 156 items (74%) are flagged.
- Cause: 173 of 457 issues carry the Elara fix-list boilerplate, and 174 issues have exactly 4 items.
  - The items are:
    - "A test that fails without the fix passes with it (CI run linked in the PR)."
    - "CI is green; integration changes also pass the lab workflow."
    - "Retrieval or token changes show a measured benchmark change…"
    - "The plan note in Elara … records what was done."
  - These are generic and mostly can't be shown at PR time. "CI is green" and "the plan note records what was done" depend on later events.
  - Bug-template issues, such as the #1008/#1015/#1025–27 family, have no items.
- The ⅔ rule is brittle in both directions.
  - It does no stemming. #1014's benchmark section covers "measured benchmark change" at length, but only 3 of 9 content words match exactly (needs 6).
  - Of the unmentioned items, 40 are short by 1 word, 29 by 2, and 44 by 3 or more.
  - A cheap suffix stemmer barely helps (29 / 32 / 16), so the misses are structural rather than a tuning problem.
  - It is also lenient in the other direction. Incidental words ("test", "fails", "passes") satisfy "A test that fails without the fix passes with it" in #955, #981 and #945.
  - The effective rule is therefore "paste the item verbatim". That passes, because the normalised substring check short-circuits.
- Closing-keyword parsing agrees with GitHub's `closingIssuesReferences` on all 80 recent merged PRs (0 mismatches).
- The title-only warning (d) fires on 10 of the 80. It also fires when the body says `Refs #N` on purpose (#1014, #1019).

### (2) Known-defects rule (b)
- The gate's rule 5 ("an entry points at a closed issue or at a PR") and rule 6 (malformed file) are in `lab-gate.mjs`. Its schema requires `issue` to be a positive integer (line 58).
- All 20 entries on `dev` have numeric `issue`, with keys `test`, `check` or `match`, and `intermittent`.
- Rule (b) `Number(d.issue) === n` over `defects[]` matches that shape and semantics. It is slightly more lenient than the gate, which is harmless.
- It reads the merge-ref checkout, so the PR's own removal of the entry counts.
- An unreadable file only warns. That is fine, because the gate reports malformed files itself.

### (3) Sticky-comment idempotence
- `edited` and `synchronize` share one concurrency group (`workflow-PR number`) with `cancel-in-progress`, so runs for one PR are serialised.
- The upsert is list, then PATCH or POST, and it matches on `startsWith(marker)`.
- The only duplicate window is a cancelled run whose POST is already in flight. No later code dedupes it, and the next run would update only the first match. The window is very narrow and I rate it P3.
- A `pull_request` run and a `merge_group` run for the same PR sit in different concurrency groups and could also race, again narrowly.
- The comment ends with `Head: <sha>`, so it is PATCHed on every push. That is "updated only when its text changes", but not stable across pushes.

### (4) `pull_request` vs `pull_request_target`
- `pull_request` is the right event. On a fork PR (the repo is public and has a CLA workflow, though 0 of the last 200 PRs were cross-repo) the token is read-only. The comment POST 403s, is caught, and the text goes to the step summary while the verdict stands. The PR checks out only the merge commit and parses `known-defects.json` as data, with no PR code executed.
- `pull_request_target` would add complexity and a write token for no gain.
- Caveat: "PR cannot edit the check it is judged by" is only true of the script. The workflow YAML itself comes from the PR's merge commit. A same-repo PR author can edit it to run the PR's own script, or to `exit 0`. This is the same trust level as `pr-evidence`, so it is not a regression, but the docs and comments overclaim.

### (5) `merge_group` resolution
- The regex accepts both `refs/heads/gh-readonly-queue/<base>/pr-N-<40hex>` and the bare form, and the PR body is then fetched live. That is sound.
- Caveat [INFERENCE]: the queue branch names only one PR. If the queue is later configured to build multi-PR groups, only the PR named in the branch is checked. The others are covered only by their `pull_request` runs.
- The queue isn't enabled yet; the only ruleset is "Require CI green" with `required_status_checks` and `pull_request`.

## Findings (blocking)

### P2 — Edited merged or closed PRs hit "already closed" and overwrite the sticky comment
- Location: `.github/workflows/issue-close-check.yml:22`, `issue-close-check.mjs:345-349`.
- `edited` also fires on closed and merged PRs. After a merge, the issues the PR closed are closed, so rule (c) reports "already closed: a merged PR cannot close it again" and fails.
- The run also PATCHes the sticky comment on the merged PR to "failed". This repo edits PR bodies after merge, for example to update evidence links.
- Fix: guard the job with `if: github.event_name == 'merge_group' || github.event.pull_request.state == 'open'`. Alternatively, make the script exit 0 when `pr.merged`/`pr.state === 'closed'`.
- Confidence about 0.6. I did not observe a post-merge run; no post-merge `edited` run showed up in the data I pulled.

### P1 (design) — Failing on unmentioned items (a) would block ~70% of PRs
- Location: `issue-close-check.mjs:354-359` and `:398-399` (`ok` is false when any item is unmentioned).
- See (1): 31 of 44 recent PRs fail, and nearly all failures are the 4 boilerplate items.
- The match tests wording, not whether the item is met. Authors would learn to paste the 4 lines, which trains box-ticking, and the sticky comment then reads as a false "passed".
- Items such as "CI is green" and "plan note records what was done" can't be met when the PR is written.
- **Recommendation for (a): comment only, never fail.** Keep the sticky comment and add a `::warning`, but let `ok` ignore unmentioned items. Keep (b) and (c) as hard failures, since they are deterministic and match the lab gate.
- If the owner wants a hard gate, restrict it to items that aren't the shared boilerplate, or require an explicit `Done when:` block in the PR body and check only that it exists.

## Minor
- The docs say "never duplicated" and the YAML comment says a PR "cannot edit the check it is judged by". Both overclaim. See (3) and (4).
- Items are checked against the event payload body, so a manual re-run after a body edit still uses the old body. A new `edited` event reruns correctly, and `merge_group` reads live.
- The warning (d) could be suppressed when the body already names the issue (`Refs #N`) to avoid sticky-comment noise on deliberately partial PRs (#1014, #1019).
- Transient GitHub API errors (5xx or rate limit) hard-fail the check ("The check could not run").
- The comment embeds issue titles and item text verbatim, so any `@mentions` in an issue body would ping from the bot comment.
- The write path in real Actions (a `pull-requests: write` token posting the comment) wasn't exercised in CI; the PR's evidence was a local shell run plus a no-op CI run.

Verdict: CHANGES — for the unmentioned-item rule (a), comment only and don't fail, for the reasons above. Also add the merged/closed-PR guard before the `issue-close` check can ever be made required.
