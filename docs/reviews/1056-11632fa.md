## Minor
1. **No test pins the non-refusal side of the rule.**
   - The server tests cover "lacks the rebase and holds unknown items → refused" and "fresh → syncs".
   - Nothing tests that a tab holding unknown items that already has the rebase is accepted. This is the "normal reconnecting tab with offline edits" case the rule must protect.
   - Nothing tests that a tab lacking the rebase but holding no unknown items is accepted.
   - `holdsUnknownItems` and `lacksRebase` have no unit tests. An inverted `lacksRebase` would still pass both new server tests.
   - I'd add one test for each (`collab-s2b.test.ts` or a pure unit test).
2. **PR body is stale.** "Runs on head d7bc115: pending" should point to `checks` 41285493699, `lab` 41285493708 and `fails-before` 41285509991. The body's evidence runs are on b1c49d1.
3. **Small input window in `rebased()`.**
   - The offer is a one-shot text snapshot. A keystroke into the old `ydoc` between `setDoc(fresh)` and the next render is not in the offer. `merge()` closes the equivalent window with a live `update` forwarder.
   - The window is about one render, so this is practically negligible.
4. **Offer shows the whole body.** The offer is the entire old body, even when the tab's only unknown items were deletions or text the relay already has. It is safe but noisy. Unsent frontmatter edits are dropped, which the PR discloses.
5. **Not fixed, disclosed in the PR.** The residue noted in #891 is a #720 browser copy that predates a rebase, which `merge()` still applies after the handshake. A rollback to older code does not record its rebases.
6. **Log noise.** `Connection.processMessages` logs a `console.error` stack for every refusal. The existing `note-too-large` refusal behaves the same way.
