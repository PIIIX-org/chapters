## Findings (blocking)
1. **The cross-database comparison catches an id-based tie-break only by chance.** See `server/test/mcp-deterministic-answers.test.ts:114-160` and `:219`.
   - **Why:** every id comes from `gen_random_uuid()` (`defaultRandom()` in `schema.ts`). Creating world B's notes and files in reverse changes the physical row order and the embed/import history. It does not change which tied row has the smaller id.
   - **How often a regression gets through:**
     - With two tied rows (twins/a and twins/b), a regression to an id tie-break goes unseen in about half of all runs.
     - With three (`parse` in three files), about one in six.
     - The probe matches this: 2/5, 4/5 and 4/5 above, and 1/5 for the real #623 on `dev`.
   - **Impact:** a PR that drops a `path` tie-break can pass its own CI. The red then shows up later on an unrelated PR, as an apparent flake.
     - That undercuts the PR's stated purpose: acceptance for #468, #470, #471, #472 and #534, and "the fix PR sees its case go red".
     - The body's "each is reproduced by the new test" holds only probabilistically.
   - **Fix:** make the precondition deterministic. After both worlds are built, compare the id order of every tied group in A and B: the twins' note ids and blocks, and the three `parse` symbol blocks and their files. Rebuild B under a fresh account until each group's order is reversed.
     - Reversed means every pair is inverted, so any id tie-break shows.
     - That takes about 2 builds for the pair and about 6 for the triple. The file takes 1.6 s in CI.
     - At minimum, assert the precondition and state in the header comment and in backend-reference §7 that detection is probabilistic.

## Minor
- `every allowlisted time key was masked` relies on the earlier cases in the file having run. It fails falsely under `-t`.
- The same-index check only asks world A twice. Within one Postgres database, an id tie-break is stable, so that half catches only randomness inside the process (Louvain, `Math.random`). It cannot catch id dependence.
- The header comment and the PR body describe reverse insertion as making the rows "inserted in opposite orders". That is true of physical order and history, but not of id order (see the finding).
- Once #1000 lands, `differs: '#623 (fixed by #1000)'` is stale; the body acknowledges this. The removal is one line, and I confirmed it passes 5 of 5 runs on the merge.
