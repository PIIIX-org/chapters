**Locks taken per path.** The advisory-lock graph has no cycle.

| Path | Locks, in order |
|---|---|
| `recomputeSemanticEdges` | node lock (exclusive), then container locks (shared, id order, one statement) |
| `mergeEntered` | node locks of the lists (exclusive, sorted), then container locks (shared, id order, one statement) |
| `removeSemanticNodes` and `transferVaultSemanticEdges` | one container, exclusive |
| `awaitSearches` | one container, exclusive, released at statement end |

- A writer never holds a container lock while waiting for a node lock.
- Exclusive takers hold only one container, so a queued exclusive request cannot close a cycle with writers.
- Writers no longer take `FOR SHARE` on the notes row, so a deleter holding the note row cannot block a writer.
- Of the 25 deadlocks the Postgres log recorded across the head runs, none involved an advisory lock; all were `ShareLock on transaction`.
- Base's writer-vs-deleter deadlock (`refresh of note … deadlock detected`) did not appear on head.

## Minor
1. **Deleters can still deadlock on edge rows (`semantic-edges.ts:469-481`, the `removeSemanticNodes` statement).**
   - Two deleters of different containers take different advisory locks, so nothing orders them. If their node sets are linked by rows, both delete the same note↔file rows in different orders. Postgres aborts one with `40P01` and its transaction rolls back.
   - Example: a vault trash (or transfer, or note delete) concurrent with a sync that removes files.
   - In my probes it hit about 1 trial in 6 under injected jitter, with no corruption. The #1017 invariant held and nothing was left half-written.
   - The class already exists on base for note-delete vs file-delete (8 failures in 40 trials there). This PR adds the bulk deleters `trashVaultRecord` and the transfer, and its text says "No deadlock", which holds only for advisory locks.
   - Suggested fix: serialize deleters per owner with one more advisory lock, or delete in a fixed order.
   - Also soften the "No deadlock" sentence in the PR body and in `backend-reference.md` §5.6.

2. **Deleting a note now waits on the vault's writers (`removeSemanticNodes` inside `storeTransaction`, `lock_timeout` 5 s).**
   - Previously a delete waited only for the note row. It now waits for the exclusive container lock, i.e. every in-flight recompute or merge in that vault, and new writers queue behind it.
   - Under load this can surface as `StoreBusyError` (a retryable "lock timeout").
   - The docs sentence "Edits to a note never wait for its recompute" holds for edits but not for deletes.

3. **Vault restore queues O(notes) unkeyed refresh jobs.**
   - Repeated trash→restore while the worker lags queues duplicates.
   - The PR discloses the once-per-restore cost; keying them like the rebuild jobs would bound it.

4. **Lock count scales with the owner's container count.** A file's recompute takes a shared lock on every live vault of its owner, and a note's on every repository. A very large container count per owner could pressure the shared lock table. The PR does not discuss this.

5. **`purgeVaultRecord` still collects `noteIds` before its transaction.** A note created in that window keeps rows until a rebuild. This is pre-existing; the container lock now makes re-reading inside the transaction possible.

6. **`checks` is red on the `collab-s3-perf` flake; re-run it.** The PR is also 18 commits behind dev, but the merge ref is already against `fb8d165`.
