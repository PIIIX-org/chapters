- **Pinned token, well-formed id for the same kind:** a wrong id is refused naming only the pin, so no other id is leaked. The refusal comes before the scope resolution.
- **Account token, id not visible to the caller:** an unseen id gets the same answer as an unknown one, and only the caller's own list is named. The `catch` branch checks `own.some(given)` against the full list, so a visible id keeps its normal error.
- **Size bound:** suggestions are capped at 5 (`ID_SUGGESTIONS`). The cap test passes the bound, but see the ordering finding below.

- **Tests fail before the fix:** the PR says the new error cases fail on dev because there are no suggestions. This is plausible from the diff, and the `mcp-tool-schema.test.ts` assertion flips from "Invalid UUID" to "not a UUID". The `fails-before` check is still pending, so this is unconfirmed.
- **CI at review time:** `checks`, `lab`, `bench (1–3)`, `evaluate` and `fails-before` are pending. `review-verdict/dev` fails with "No review of 806e70f". `attribution`, `plan`, `issue-close`, `pr-evidence` and `CLAssistant` pass. The PR body says no harness change, and only the `phase-3` label is present.

## Findings (blocking, path:line)

1. **`server/src/mcp/server.ts`, `idRefusal`, around lines 673–684: a pinned token's malformed id of the other kind lists the account's ids and names.**
   - `pin` is set only when `auth.connection.scope === kind`. A vault-pinned token that sends a malformed `repositoryId` has `pin = null`. It falls through to the account branch, where `listAccessibleRepositories(auth.user.id)` returns up to 5 `<id> (<name>)` entries.
   - The same happens for a repository-pinned token with a malformed `vaultId`.
   - This runs before `def.ids` and the scope refusals. Pinned tokens must not enumerate account resources: `list_vaults` and `list_repositories` are `scope: 'account'`, and `requireAccountScope` hard-rejects pinned tokens.
   - It is a scope-bypass leak of names and ids from the user's account. A well-formed foreign id is refused later by the scope check, so only the malformed path leaks.
   - The new tests only cover a malformed id of the pinned kind, so they do not catch this.
   - Fix: only build the account suggestions when `auth.connection.scope === 'account'`. Otherwise refuse with the existing scope error, with no suggestions or with the pin only. Add a test for vault-pinned plus malformed `repositoryId` and repository-pinned plus malformed `vaultId`, asserting no suggestions.

2. **`server/src/mcp/server.ts`, `idRefusal` and the `catch` branch (`own.slice(0, ID_SUGGESTIONS)`), and the underlying list functions: the 5 suggestions are non-deterministic.**
   - Both list functions have no `ORDER BY`. They return Map insertion order built from three unordered queries (`owned`, `direct`, `viaTeam`).
   - With more than 5 accessible items, which 5 are named can change between calls and as the database changes.
   - In the account branch the agent's intended id may be absent from the 5. The refusal also appends to the heap, so a mis-copied id's nearest match is never preferred.
   - The cap test only checks `toHaveLength(5)`, so it would not catch this.
   - Fix: sort deterministically before slicing, for example by name then id, or by closeness to the requested id. Add a test that two refusals give identical suggestions with more than 5 ids.

3. **`Closes #1101` overstates what is done.** The issue's "Done when" has several items the PR does not meet or does not cover:
   - **Test coverage:** it asks for tests for "owner / shared / revoked / other-account, pinned and unpinned". The new tests have no shared or revoked cases.
   - **Trial run:** the Elara arm of the agent trial on a pinned token completing T1 with no id error, with a run linked, is not delivered. The PR lists the trial as "Not covered".
   - **Proposal item 3:** the trial and premise benchmark stopping passing the id for pinned tokens is also "Not covered".
   - **Tool families:** the account-token tests cover only `browse_repository` and `browse_vault`, not each tool family as the issue asks.
   - The PR should say `Refs #1101` instead of `Closes`, or finish those items. Do not lose gold on any suite.

## Minor
- **`server.ts` `catch`:**
  - The `unseen` detection depends on `err.message === 'not found'`, which is a string match on a message. If any `NOT_FOUND` text changes, suggestions vanish silently.
  - It picks `repositoryId` over `vaultId` when both are present, so a call with both gets suggestions only for the repository.
  - It repeats the account-list read that `idRefusal` does. A shared helper would be tidier.
- **Tests:** the pinned-mismatch test for a well-formed foreign id does not assert `error.code`. It would not fail if the code changed between `TOOL_NOT_ALLOWED` and `INVALID_ARGUMENT`.
- **Code and docs:** the refusal is `TOOL_NOT_ALLOWED` for a well-formed mismatched id but `INVALID_ARGUMENT` for a malformed one. That asymmetry is not stated in the manuals or `backend-reference.md`.
- **Budgets:** the PR claims numbers I could not reproduce. The reviewer or CI should confirm the `mcp-tool-budget` and `mcp-tool-schema` (admin 43,000) results before merge.
- **Review verdict check:** `review-verdict/dev` is failing because no review is posted for this head. It resolves only after a `VERDICT: MERGE` for 806e70f, which this review does not give.

Verdict: CHANGES
