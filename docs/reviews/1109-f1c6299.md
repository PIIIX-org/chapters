# Review of PIIIX-org/chapters#1109

Head reviewed: a58df6132089310e102c1c2eff103552cab603f1

I read the diff and the code it touches. I did not run any tests: there was no database here, and CI is still running.

## Scope checked

- **Files:** `graph/local-graph.ts` (new), `notes/store.ts` (removals), `notes/routes.ts`, `notes/staleness.ts`, the `read_note` change in `mcp/server.ts`, the new test file, `backend-reference.md` and both manuals.
- **Parity:** REST local graph against the MCP `graph` walk (`neighborhood`), and `getIncomingLinks` against `backlinksOf`.
- **Access and gold list:** access scope and the access matrices, the gold-list paths, CI status, and the issue #472 done-when.

## Verified

- **Manuals:** `skills/chapters/references/mcp-tools.md` and `skills/elara/references/mcp-tools.md` are byte-identical at head (`cmp`).
- **Dead code:** the old `getLocalGraph`, its types and the `semanticEdges` import in `store.ts` were removed. The only remaining caller is `routes.ts`, which now imports the new `graph/local-graph.ts`. The client reads the same JSON shape.
- **Local graph, scope and bounds:**
  - `neighborhood()` is called with `vaultIds: [vaultId]` and `repositoryIds: []`, and the route already checks vault access.
  - Every node and backlink query filters `isNull(deletedAt)`, so deleted notes are excluded and nothing crosses vaults.
  - The 50-node cap, the nearest-first-then-path order, and the center always sitting at rank 0 hold.
  - Query count is constant: a handful of queries per ring, one name lookup, no N+1.
- **Backlink lines:** `backlinksOf` is ordered by path with `COLLATE "C"`, then start line. It converts body-relative lines with `bodyStartLine`. The REST route reuses it, so the lines match what MCP `graph` lists.
- **Gold list:** the PR touches none of `search/**`, `mcp/{response,read-targets,session-reads}.ts` or `notes/note-blocks.ts`. `notes/store.ts` and `graph/` are not on the list either. `mcp/server.ts` is not on the list.
- **Token budgets:** no tool description text changed. Only the manual and the `read_note` answer head gained `drift`.
- **Scope of access matrices:** the existing REST matrices for `backlinks/*` and `local-graph/*` (`server/test/access-matrix.test.ts` lines 297 and 309, `lab/tests/access-matrix.test.ts` lines 160 and 163) still cover those routes. The added `links` field adds no new route.
- **CI:** `fails-before`, `lab`, `plan`, `evaluate` and `attribution` pass. `bench` and `checks` are still pending. `pr-evidence` and `review-verdict/dev` fail. I did not run the tests myself.

## Findings (blocking, path:line)

1. **`server/src/graph/local-graph.ts:~49` (REST local graph) and `server/src/notes/routes.ts:~280` (backlinks): wikilinks that are not written as the exact note path are dropped.**
   - `note_links.target_path` stores the link text as written. `extractWikilinkLocations` only trims it, so `[[centre]]`, `[[docs/centre.md]]` and `[[/docs/centre]]` are stored as-is.
   - The removed `getLocalGraph` resolved targets by path, path without `.md`, and name. `getIncomingLinks` still does (`store.ts` ~1776, candidates are fullPath, `.md`, name, name.md).
   - `neighborhood` and `backlinksOf` join `target.path = note_links.target_path` and `eq(noteLinks.targetPath, center.path)`. That is exact-path only.
   - Result 1: the REST local graph silently loses every edge and neighbor reached through a short-name or `.md` link. That is a common wikilink style, so this is a regression in the REST graph. The PR's "Not covered" section does not mention it.
   - Result 2: the REST backlinks list still includes notes that link by name, because `getIncomingLinks` resolves them. In the route, `lines.filter(l => l.path === b.path)` finds no rows for those notes, so they come back with `links: []`. That contradicts the stated "one item per linking note with its lines".
   - The new test only uses full-path links, so it cannot catch this. Fix: either resolve name and `.md` targets in the shared walk (`neighbors.ts`, which also changes MCP), or make REST use the same candidate set. Then add a fails-before case with `[[centre]]` and `[[docs/centre.md]]`.

2. **`server/src/mcp/server.ts:~1502` with `server/src/notes/staleness.ts` (`noteDrift`): drift ignores the connection's scope and leaks repository data.**
   - `noteDrift` uses `listAccessibleRepositories(auth.user.id)`, which is every repository the user can read, without checking the connection scope.
   - The `read_note` answer for a vault-pinned token then includes repo resource strings, "file does not exist" details and hash prefixes for repositories outside the token's pin.
   - The server states that scope is "hard, never narrowed". The comparable code at `server.ts` ~3052 uses `auth.connection.scope === 'account' ? … : []`.
   - Fix: compute drift only for repositories the connection may reach. That means all accessible repositories for an account token, only the pinned one for a repository token, and none for a vault token. Add a test with a vault-scoped connection.

3. **Missing access test for the new cross-resource data on `read_note`.**
   - `drift` returns data from repositories, which is a different permission domain from the vault the note lives in. The `read_note` access matrices in `server/test/access-matrix.test.ts` (line 171) and the lab one use a note with no repo references.
   - There is no case showing that a vault reader without repository access gets no `drift` for a note that references an inaccessible repository.
   - The owner rule says new read surfaces go in both matrices, so add that case to both.

4. **`pr-evidence` is red on the head, so the PR cannot merge as is.**
   - The "58 files, 666 tests passed locally" bullet has no link to a run, PR or commit, which the checker requires.
   - `review-verdict/dev` is also failing because no review of this head exists yet.

## Minor

- **Drift gate (`staleness.ts` `noteDrift`):** the `/repo:|code:/` regex on the body also matches prose like "code:" or "barcode:". Such a note then runs `listAccessibleRepositories` (4 queries) plus 2–3 queries per accessible repository on every first-page `read_note`.
  - A match on `[[(repo|code):` and on `sources` entries would avoid this.
  - Even for real references, the repository count multiplies the work. Checking only the repositories actually named would keep it constant.
- **Hash-mismatch coverage:** the new test covers `deleted_file` and `missing_symbol` only. It has no `hash_mismatch` case, and no case for frontmatter `sources`, which `read_note` docs advertise.
- **Backlink join:** `lines.filter(...)` runs once per item over up to 1,001 rows. Group by path once instead.
- **Test gaps:** there are no depth-2 or 50-node-limit REST cases. The old route's depth and limit behaviour is therefore unpinned under the new walk.

Verdict: CHANGES
