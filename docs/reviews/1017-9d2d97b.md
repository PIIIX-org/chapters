# Review: #1017 `fix: semantic edges independent of embed order (#1007)` @ 9d2d97b6

## Verdict: **incorrect**. The fix works, but it should not merge as it is.

The order fix is sound. With exact search, the stored edges come out as a pure function of the final vectors. The write path that keeps them current has two cost defects, and one of them turns this PR's own CI red. I measured this on my own Postgres (pgvector pg17) with the fake embedder.

## Findings

### 1. [P1] Exact ties with the K-th neighbour make an embed recompute every tied list, so the cost grows with the square of the file count
`server/src/search/semantic-edges.ts:255-260, 273-274`

- **The cause:** `enteredBy` treats a similarity equal to a candidate's stored K-th (`>= s.kth - slack`, and the weak scan's `kth <= edge + slack`) as "enters", whatever the path order. When files have identical similarities to each other (empty `__init__.py`, boilerplate, the CI fixture's `starve query words w{i}`), every new file therefore recomputes every earlier file's list.
- **The scale:** for an `agent_push` of N such files, `flushExtraction` took:

  | files | dev | PR head |
  |---|---|---|
  | 50 | 1.8 s | 17.5 s |
  | 100 | 3.1 s | 50.6 s |
  | 200 | 6.1 s | 212 s |

  At 100 files I logged 10,082 `pg_advisory_xact_lock` calls, which is about 100 recomputes per file instead of 1.
- **It is CI's failure:** the `checks` run for this PR failed. `search-deterministic-vectors` ("a small repository inside a big instance…") timed out at 120 s, and `embed-restart`'s `beforeAll` timed out at 600 s. Dev a2ef7d10 and 65bdb534 are green. I reproduced the first test locally: 9 s on dev, a 120 s timeout on head.
- **Suggested fix:** on an exact tie with the K-th row (compare as `real`), let N enter only if it ranks before that row's target by the same key `byRank` uses: path, then type, then id.

### 2. [P1] `enteredBy`'s last check spills gigabytes to temp files for a long note
`server/src/search/semantic-edges.ts:264-274`

- **The cause:** the query groups every candidate query vector × new vector pair in one `HashAggregate`. Each row carries both 1.5 KB vectors.
- **The measurement:** a vault of 10,000 notes (about 45k blocks) plus 1,000 files, threshold 0.75. A new 300-block note took **1.8 s on dev and 153–210 s on head**. `EXPLAIN ANALYZE` of that one statement shows 12,753,900 rows, `Disk Usage: 26937920kB` (27 GB of temp files) and 128 s.
  - The 425 recomputes cost only about 5 s of that.
  - A 40-block note went from 2.0 s to 5.4 s.
- **Why it matters:** the embedding worker is single-threaded, so one pasted long document stalls embedding for minutes. On a small disk the temp files can fail the statement. A refresh that fails after the commit is never retried, because the retry sees `changed = false`.
- **Suggested fix:** take the minimum per candidate inside a lateral subquery. Tested on the same data: same 393 rows, 2.0 s, no temp file.

```suggestion
  const entered = (await client.execute(sql`
    SELECT c.id
    FROM unnest(${`{${[...candidates].join(',')}}`}::uuid[]) AS c(id)
    ${liveOwner(ownerType, sql`c.id`)}
    CROSS JOIN LATERAL (
      SELECT 1 - min(q.vec <=> v.vec) AS similarity
      FROM (${queryVectors(ownerType, sql`ARRAY[c.id]`)}) q CROSS JOIN (${vectors}) v
    ) d
    CROSS JOIN LATERAL (
      SELECT count(*) AS n, min(e.similarity) AS kth FROM semantic_edges e WHERE e.node_a_type = ${ownerType} AND e.node_a_id = c.id
    ) s
    WHERE d.similarity >= ${config.semanticThreshold}
      AND (s.n < ${config.semanticK} OR d.similarity >= s.kth - ${STORED_SIMILARITY_SLACK})`)) as unknown as Array<{ id: string }>
```

### 3. [P3] The path tie-break does not separate equal paths in different repositories or vaults
`server/src/search/semantic-edges.ts:99, 127-131`

- **The cause:** a note's code reach is all of its owner's repositories, and a file's note reach is all live vaults. So identical files with the same path in two repositories (`tsconfig.json`, `LICENSE`, forks; the PR's own 8-repository fixture) tie on similarity, path and type, and fall through to `owner_id`.
- **The effect:** at the K cut, which copy is kept still differs between instances.
- **Suggested fix:** order by the container's name before the path.
