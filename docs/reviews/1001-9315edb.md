## Findings (blocking)
1. **#463's own clause is still unpinned, but the PR closes #463.** Relevant lines: `server/test/embed-restart.test.ts:111-116` and `:132`, and the doc claim at `docs/agents/backend-reference.md:2915`.
   - #463 asks to "re-embed notes whose embedding is stale after a restart, not only notes with no embedding". In the boot catch-up this is the `owner_version = n.seq` part of `noteBlocksCurrentSql()`, used at `embedding-queue.ts:126`.
   - Every new restart scenario has a job row for the current key. `reboot()` reaches the job only through the expired lease in `claimJob`, so the catch-up's staleness check is never used.
   - Mutation R5 rewrites the catch-up `WHERE` to "has any blocks + current embedder/chunker", which drops the seq comparison. Under it, the new tests and the whole server suite pass: 1592 passed, 3 failed. The 3 failures were load timeouts in `store-s2a2-boot` and `collab-s3-perf`; both files pass when rerun alone with the mutation still applied.
   - This path happens in production. The 0021 trigger bumps `seq` on any `UPDATE` of the body or frontmatter, including an `UPDATE` run directly in SQL or by pre-#494 code after a rollback (backup.md §5's additive rule), and neither inserts a job.
   - The fix is a short scratch test I wrote in `embed-restart`. It creates a note at V1, runs `UPDATE notes SET body = V2` in SQL (the trigger bumps `seq`; there is no job), then calls `scheduleMissingEmbeddings()` and `flushEmbeddings()`, and expects the blocks at the new `seq`. It passes on the head and fails under R5 (`expected ['1'] to deeply equal ['2']`). It was deleted afterwards. Add this case before `Closes #463`.
