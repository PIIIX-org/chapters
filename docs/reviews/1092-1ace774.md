## Verified

## Findings (blocking)
- **server/test/collab-s3-perf.test.ts:137-145 — the teardown wait is a timing heuristic, not a wait on the fold.**
  - `afterUnloadDocument` in `collab-server.ts` (~L704-719) runs `compactCollabState(...)` after the document is already out of the documents map. It tracks that promise in the private `unloadFolds` set, which `CollabRelay` does not expose. `destroy()` is the only thing that waits on it.
  - `getDocumentsCount() === 0` therefore becomes true when the fold of the 1 MiB note is only beginning. The revision-count poll then stops after two equal samples 500 ms apart.
  - If the compaction takes longer than about 500 ms to store its row, the poll sees a stable count, returns, and attempt 2 starts while the fold is still running. That is the same 1 MiB fold that caused the 254→630 ms regression.
  - The poll also does not tell "fold finished" from "fold not yet landed". It matches the original failure mode on a slow runner, where the max in the log is already 809 ms.
  - Suggested fix: make the wait deterministic. For example, expose an `idle()` or unload-folds promise on `CollabRelay` and `await` it in the `finally`. Alternatively, wait until the note's revision count goes up and the CRDT tail is compacted, instead of waiting for the count to stop changing.

## Minor
- The retry path is not exercised in the CI log, since the first attempt passed, so there is no evidence that attempt 2 now measures cleanly. The 204 ms p95 with a 250 ms budget leaves little headroom.
- A timeout in the `finally` waits (30 s each) would replace the original assertion error when attempt 1 fails, hiding the real p95 failure.
- If a `--retry` fires, the same app, relay and DB are reused, not a fresh server. The PR title and the comment on `let attempt` ("each attempt ... closes its own providers") are accurate only for providers and notes.

## Previous blockers
1. **The wait must be on the relay's unload fold, not a heuristic: resolved.**
   - `idle()` (`collab-server.ts:789-797`) waits for `getDocumentsCount() === 0`, then does `await Promise.all([...unloadFolds])`. It sleeps 10 ms and re-checks that both the document count and `unloadFolds.size` are 0, looping otherwise.
   - `unloadFolds` is the same private set that `afterUnloadDocument` fills with the `compactCollabState` promise (`:714-721`).
   - Hocuspocus deletes the document from its map, then calls `afterUnloadDocument` after only a few promise-chain microtask ticks. The only extension is the config object itself, so there is no I/O in between. `unloadFolds.add(fold)` runs synchronously inside the hook. The 10 ms sleep followed by the re-check therefore cannot miss a registration.
   - **Debounce flush:** the last connection closing calls `debouncer.executeNow` on the pending store. The document stays in the map until that store has run and a `setTimeout(0)` unload follows, so `getDocumentsCount()` covers the flush as well.
   - **Teardown order:** `finally` runs `providers.forEach(p => p.destroy())` and then `await collab.idle()` (test `:134-137`). If the server has not yet seen the close, the document count is still above 0, so `idle()` just waits.
   - **Production safety:** the only caller is the perf test (grep over `server/src` and `server/test`). `CollabRelay` is only produced by `startCollabServer`. `idle()` leaks no timers or promises; it only polls and awaits a copy of the set, and each fold promise already has a `.catch`.
