- **What is reported, to whom, how:** the report stays on the instance. It is a pull-only report: `GET /api/usage/report` (the caller's account), `?scope=instance` for the `owner`/`superadmin`/`admin` roles, and the MCP tool `usage_report` (admin profile only, account-scoped tokens only). There is no outbound POST, file or schedule; grepping `server/src/usage` finds no `fetch` or URL.
- **Opt-in:** `instance_state.usage_report_enabled` defaults to `false` (migration), and `loadUsageSetting` falls back to `false`. Only `PUT /api/usage/settings` changes it, behind `requireAdmin`, and the change is logged as the security event `usage_report_changed`. While it is off, `withUsage` just calls the handler.
- **Instance identity:** none. No instance id exists and nothing leaves the instance. The token id and `session_id` are stored as salted SHA-256 truncated to 64 bits; the salt is random per instance, kept only in the database and not in backups.
- **Payload:**
  - Rows hold only ids, numbers and hashes. Queries are stored as a hash, their length and a script guess; the filters kept are only `everywhere`/`symbols`/`limit`/`kind`.
  - A read is stored by id; the path is used inside the INSERT only and not kept.
  - No email, token or path is stored.
- **Retention:** raw rows 7 days, then per-day rollups for 30 days. Pruning runs at boot, hourly while recording, and on each report. Rows are deleted with the account (`ON DELETE CASCADE` on `users`).

## Findings (blocking)
1. **A revoked share still reveals the note's current path and id** — `server/src/usage/report.ts:195-197`.
   - `fallbackSection` joins `notes`/`repository_files` by id with no access or ownership check. This contradicts the account scope's own contract ("notes of the vaults it owns"); `never_read` does filter on `v.owner_id`.
   - Any client can send `notifications/elara/client_event`, so a reader can put this to use deliberately.
   - Reproduced:
     1. B shares a vault with A; A's admin token reads `docs/harmless` and sends `local_fallback`.
     2. B revokes the share. A's `read_note` now returns `NOT_FOUND`.
     3. B renames the note to `docs/layoffs-acme-2027`.
     4. A's REST report and A's `usage_report` both return `notes_read_before: [{id, vault_id, path: "docs/layoffs-acme-2027"}]`.
   - The same leak applies to repository files after a repository share is revoked.
   - Fix: restrict the join to vaults and repositories the account currently owns (or currently has access to), as `never_read` does.
2. **The instance view lets an admin confirm another account's exact queries** — `server/src/usage/report.ts:147` (`query_hash` grouped across accounts with one instance-wide salt).
   - An admin's account report shows their own `query_hash`. The instance report groups the same hash across all accounts and shows a count.
   - Reproduced: the victim searched "Merger With Globex" and the admin searched "merger with globex". Admin account view: `{query_hash:"453eb97bcc837fbb",count:1}`; instance view: same hash, `count:2`.
   - Admins have no read access to other users' vaults (`isInstanceAdmin` is used only for perspectives and this report). This oracle therefore lets an admin test guessed query text from other tenants, which goes against "aggregates only" and the checklist's privacy statement.
   - Fix: drop `query_hash` from instance-scope lists (keep counts, length and language), or include the account id in the hash.
3. **The search section of the report is quadratic, and the report never finished on a modest dataset** — `server/src/usage/report.ts:141-143`.
   - The correlated `EXISTS` scans the materialised `ev` CTE for every search row, with no index.
   - Measured: 70,000 raw rows (21,000 searches, 50 tokens; about 10k calls a day over the 7-day window). The instance report's `searchSection` was still running at 189 s, when I killed it. The REST request and the MCP `usage_report` call block for that whole time, and each report runs `flushUsage` + `pruneUsage` first.
   - The PR measured the recorder's cost but not the report's.
   - Fix: compute the "next 5 calls" with window functions (`lead` over `(token ORDER BY id)` / an array of the next 5 `target_id`s) instead of the correlated subquery.
4. **The PR conflicts with dev and its CI is from an old merge ref** (`mergeable: CONFLICTING`).
   - Conflicts: `server/drizzle/meta/_journal.json` (0053 vs 0058), `docs/self-hosting/backup.md` (0053 vs 0058 rollback entries), `docs/agents/backend-reference.md`.
   - The green CI is on a merge ref built on 438e63b. Rebase onto dev 7d02a03, then rerun checks and lab.

## Minor
- `server/src/usage/recorder.ts:267,373`: a read's path is resolved to an id at flush time (up to `FLUSH_MS`, or whenever the next report runs), not at call time. In my first probe, a `read_note` followed within the flush window by `rename_note` was stored with `target_id: null`. The note then counted as never read, and its read was lost from `no_useful_hit` and from the fallback section. The answer already carries the note's/file's id; record that instead.
