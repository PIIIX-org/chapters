## Verified
- **What `explain` joins:**
  - `callers` and `tests` come from `code_edges` via `codeSites`, with the same ordering as the other `refs` views (resolved first, then path, line, column, kind).
  - `callers` is not resolved-only: it includes textual rows, and guessed member calls are excluded by `NOT_GUESSED_MEMBER`.
  - `tests` keeps member rows.
  - Rows carry a `confidence` field, so the reader can tell resolved from textual.
- **How notes citing a symbol are matched:**
  - They are matched by the definition's file, not the symbol.
  - The match is `note_links.target_path`, lowercased, equal to `repo:<name>/<path>` or `repo:<id>/<path>`.
  - The `#anchor` is dropped by the link regex, so every symbol in a file gets the same `cites`.
  - This is documented as "cite its file". The PR title and the "which notes cite it" framing overstate it slightly.
- **Access:**
  - `requireRepositoryAccess` runs first, and a stranger gets the same error as for a missing repository.
  - `cites` filters `notes.vaultId IN listAccessibleVaults(user)`, which covers owned, user-shared and team-shared vaults (and an inactive user gets none).
  - Deleted notes are excluded.
  - A repository-pinned token reads no vault, so it gets no `cites`.
  - A note's text appears only through `context`, `at` and `vault` of readable vaults.
  - No leak found for "repo shared, vault not": `vaultIds` comes only from the caller's own accessible vaults.
- **Bounds and ordering:**
  - 5 callers, 3 tests and 5 cites are shown, each fetched with a lookahead so `ranked` reports `>5`.
  - Cite fetch is capped at 50 rows (`slice(0, 50)` drops the lookahead row, so the cap is invisible but harmless).
  - Cites are ordered by note path (`COLLATE "C"`), vault id, start line. The link key `(note, startLine, target)` makes ties practically impossible, so the order is deterministic without ids.
  - The line offsets reuse `bodyStartLine`, as backlinks do.
- **Manuals and docs:** `skills/chapters/references/mcp-tools.md` and `skills/elara/references/mcp-tools.md` have identical hunks (same blob hashes `f117133a..745da8c2`), and the two SKILL.md lines are identical. The `refs` parameter description is updated.

## Findings (blocking, `path:line`)
1. `server/test/access-matrix.test.ts:158` and `server/test/mcp-explain.test.ts`: the hole this review was asked to check is untested, though the code appears correct. `shareBoth` grants the vault and the repository together, and revoke removes both. Revoked and unrelated therefore fail at the repository check and never reach the vault filter in `citationsOf`. Nothing tests "repository readable, vault not": the stranger case in `mcp-explain.test.ts` cannot read the repository either. If `listAccessibleVaults` were swapped for all vaults, every new test would still pass. Add a case in `mcp-explain.test.ts` where the repository is shared with a second account but the vault is not. It should assert that `cites` is empty and that neither `why-persist` nor the vault id appears in the answer. A vault-shared and repository-shared account should still see the note. Do the same in the matrix, or document why it cannot apply there.
2. `server/src/repositories/explain.ts:50`: `lower(${noteLinks.targetPath}) IN (...)` cannot use `note_links_target_idx`, which is on the raw `target_path` and which every other lookup here uses with plain equality. Postgres will probably scan all link rows of the readable vaults on every `explain`. Use the indexed column: either compare `targetPath` against the case variants, or use `ILIKE`/`citext` as `staleness.ts` does. At minimum, check `EXPLAIN` on a large link table.
3. `server/src/repositories/explain.ts:42`: the matched link forms are narrower than the repo's own resolver (`repoLinkTarget` in `graph/assemble.ts:243-263`, also `staleness.ts:70`). That resolver accepts `repo:`, `code:` and `<name>:<path>` / `repo:<name>:<path>`. `explain` matches only `repo:<name|id>/<path>`, so a note citing `[[code:name/src/x.ts]]` or `[[repo:name:src/x.ts]]` is listed by `graph neighborsOf` but not by `explain`, and the manual does not say so. Either accept the same targets or state the narrower rule in the manual and backend-reference.

## Minor
- Lowercasing both the repository name and the path (`explain.ts:42`) makes a citation of `src/Foo.ts` count as a citation of `src/foo.ts` when both files exist. The graph resolver is case-sensitive.
- `cites` is per link, not per note. One note with five links to the file fills all five slots and hides other notes. Collapse to one entry per note, or say so.
- Repository names are not unique in the schema. A note in a readable vault that cites `repo:foo/...` for the other account's repository named `foo` also appears under your `foo`. This is the same matching as `staleness.ts`, so it is a known limitation, but the manual does not mention it.
- The comment on `CITATION_ROWS` ("one more than the section shows") is wrong: 50 rows are kept and 5 are shown. The `slice` is needed, but the lookahead row it drops is unused.
- `limit` and `everywhere` are accepted and ignored with `refs: "explain"`, because `refsArguments` is skipped. `depth` is rejected explicitly.
- The `deterministic-answers` question that explains `upload` claims "a citing note". I did not confirm that the fixture world has a note citing `src/upload.ts`, so `cites` may be empty there.
