## Verified

### 1. Regex semantics and ReDoS
- **Regex, not literal.** The pattern runs as a Postgres ARE through `~` and `regexp_split_to_table`, not as a JS `RegExp`.
- **Translation.** `translatePattern` rewrites `\b` and `\B` to `\y` and `\Y`, and refuses back references `\1`–`\9` (also inside classes). It correctly skips escaped backslashes and `[[:class:]]`.
- **Invalid patterns.** They are validated up front with `SELECT '' ~ $1`. SQLSTATE 2201B/2201C maps to `INVALID_ARGUMENT`.
- **Bounds.** Pattern is 1–300 characters. Each statement runs under `statement_timeout` 4 s (`set_config(..., true)`, transaction-local), and 57014 maps to a retryable `BUSY`.
- **Tests.** `^(a+)+$` and `(a|aa)+$` on a 5,000-`a` line stay under 5 s. A `BUSY` test with `statementMs = 20` asserts the code, `retryable` and the "narrow" message.

### 2. Scope and access
- **Scope resolver.** `scope: 'vault-or-repo'` uses `resolveResourceSet` for pinned tokens, and `listAccessibleVaults`/`listAccessibleRepositories` for `everywhere`. That is the same path `search` uses, and `grepTargets` only reads those ids.
- **Access matrices.** Both matrices have three entries each (vault, repository, everywhere with `kind: 'listing'`). Their identifiers are the path and the marker text, and the lab fixtures (`file`, `source`, `mark`) exist.
- **Other tests.** `mcp-scope` and `mcp-tool-profiles` are updated, and the lab `scoped-tokens` file has an `argsFor` entry plus `READER_ON_VAULT`. `mcp-grep.test.ts` shows another account's vault or repository answers `NOT_FOUND`, and `everywhere` never lists it.

### 3. Cost and determinism
- **Scan indexes.** Candidate queries use `ORDER BY path COLLATE "C"`. The existing indexes `notes_vault_path_c_live` and `repository_files_repo_path_c` serve that order.
- **Content scanning.** `content`/`body` is scanned for every file in scope, in 500-file chunks. That is real work, but capped at 20,000 files, 256 MB, 10 s and 4 s per statement. A cap ends the list with `{capped:{files,after}}` and a cursor.
- **Test coverage.** The limits test covers the cap marker, the cursor continuing, and `scanned`.
- **Ordering.** Order is vaults then repositories (by name, then id), then path in code-unit order, then line.
- **Paging.** Pages hold 50 hits and the keyset resume is correct. I traced the `>=` versus `>` handling (`PAST_FILE`), the `(path > after OR n > afterLine)` filter and the chunk loop, and found no skipped or duplicated lines.

### 4. Secrets

## Minor
1. **Per-row scan of the whole file for blank lines.** `server/src/repositories/grep.ts:225-226`.
   - The "no empty line after a final `\n`" exclusion calls `right(content,1)`, `length(content)` and `replace(content, chr(10), '')` on the whole document for every output row where `l.line = ''`.
   - That only runs when the pattern matches empty lines (`^$`, `^\s*$`, `.*`, `x*`), so cost is O(blank lines × file size).
   - On a multi-MB file with tens of thousands of blank lines that can hit the 4 s timeout and answer `BUSY`.
   - Fix: compute the trailing-empty check once per file, for example from `regexp_split_to_array`/`array_length` in a per-file subquery, or filter the last row via a single `n = max(n)` test.

2. **Cursor holds a target index, not a target id.** `server/src/mcp/grep.ts:27,39`.
   - The cursor stores `c`, the position in the sorted target list. If a vault or repository is added, removed or unshared between pages (or the name order changes), the same `c` points at a different target and hits are skipped or repeated without notice.
   - `search`'s ranked cursor has an id guard; this one has none.
   - Encoding the target id (`kind:id`) in the position would avoid it.

3. **A chunk's bytes are checked only after the scan.** `server/src/repositories/grep.ts:211`.
   - The 256 MB cap is tested before each 500-file chunk, so a chunk of large files is read whole under one 4 s statement.
   - Repositories with many large files at a path prefix can answer `BUSY` with no position, where a `capped` marker would have given progress.
   - The advice to narrow with `path` works, so this is only usability.

4. **No concurrency control on a long DB hold.**
   - One grep can hold a pooled connection for up to about 10 s plus the last statement.
   - The only throttle is `MCP_RATE_LIMIT` (120 per connection per minute), with no per-tool weight. One agent could therefore pin the pool [INFERENCE: depends on `ELARA_DATABASE_POOL_SIZE`, which I did not read].
   - A per-process semaphore on grep would bound it.
