## Findings (blocking)
1. `server/src/monitoring/sampler.ts:15-17`: `elara_jobs_oldest_pending_age_seconds` measures the age of the oldest row's original `created_at`, not how long a job has been waiting. Re-enqueued jobs keep that old `created_at`.
   - `onJobConflict` (`jobs/durable.ts`), `recomputeJobs` (`semantic-edges.ts:619`) and the other re-enqueue paths reset `id`, `done_at`, `attempts` and `lease_until` on conflict, but never `created_at`.
   - The `semantic_edges:<type>:<id>` key is stable per node, so every edit or delete of a note that has been through the queue before re-queues the same row.
   - The `pnpm reindex` path (`rerun: 'finished'`) does the same for `embed_note`.
   - I reproduced the query on a throwaway Postgres. A row finished 30 days ago and re-queued by that `ON CONFLICT` update was reported as `pending=1 oldest=2592000.0` seconds.
   - So `{kind="semantic_edges"}` reads weeks or months, and the documented "oldest age above 15 min for `extract` or `embed_note`" alert fires falsely on any reindex or re-queue. The body and docs call the metric the age of the oldest job not done.
   - Fix options: add `created_at = now()` to the re-enqueue `DO UPDATE` clauses (with a migration-free change in `durable.ts` and `semantic-edges.ts`), or measure from a column that is reset on re-run. Add a test that re-queues a finished job and checks the age.

## Minor
- **Docs alert mismatch:** `backend-reference.md` tells the operator to check `elara_jobs_total{outcome="succeeded"}` "for that kind" (`extract`, `embed_note`). Those series are labelled with monitoring kinds (`extraction`, `embedding`), so the suggested query returns nothing.
- **Sampler stop not wired to shutdown:** `index.ts` discards the function `startMetricsSampler()` returns. The timer is unref'd and the process calls `process.exit`, so this is harmless. A sample firing during `sql.end` would only log one warning.
- **Evidence links:** the body links the cancelled `pr-evidence` run 41212702188 and the cancelled `fails-before` run 41212702121. The successful reruns are 41212785245 and 41212785238. The "commands and output in the head commit's files" claim links to a test file, not to run output.
- **Max gauge limitation:** `event_loop_lag_max` is a per-15 s gauge. A scraper polling at 60 s or slower will miss spikes between scrapes, so the "max above 1 s once" alert is only reliable with a scrape interval of 15 s or less. This is worth one line in the docs.
- **Test timing:** the event-loop test asserts `max < 0.05 s` after a 40 ms sleep. That is timing-sensitive on a loaded runner but passed in CI.
- **`jobs_pending` cost:** the 15 s `count(*) GROUP BY kind` is O(pending rows). With a large reindex backlog it scans the whole backlog each time, and the heap fetches are not "index-only". I didn't measure it, so I'm not blocking on it.
