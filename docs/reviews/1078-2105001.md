# Review of PIIIX-org/chapters#1078 — feat: a read greps its document, the handle of a large result (#423)

## Scope checked
- Diff of the 11 files: `read-targets.ts`, `server.ts`, `instructions.ts`, both manuals, `SKILL.md`, both access matrices, and the tests.
- Surrounding code in `response.ts` (text-section rendering, cursors, `narrow`), `session-reads.ts` (`inSession`) and `checkReadArgs`.
- CI status of the PR's checks.

## Verified
- **Regex and ReDoS:** `grep` is a literal, not a regex. The code uses `includes`, with smart-case folding via `toLowerCase`, and the pattern is capped at 200 characters. So the `(a+)+$` probe has no effect, and the scan is linear in document size. It does one `toLowerCase` per line, plus context rows that are re-folded, with no backtracking.
- **Line numbers:** `read_note` greps the projected file (`renderNoteFile`), so numbering includes the frontmatter, the same as `lines` targets. The new test checks `bodyStart - 1 + n`. `read_file` uses the file's own numbering.
- **`if_rev`:** `unchanged` is returned before targets are evaluated, on a first page only. This is existing behaviour for every target kind.
- **`session_id`:** the `matches` section has no `lines: true`, so `inSession` skips it. A grep result is never replaced by a `same_as` reference, and no stale reference can result.
- **Cursor paging:** the cursor guard is the matches text, recomputed from the document on every page. A changed document gives `CURSOR_STALE`. The paging test shows the concatenated pages equal the unpaged result.
- **Budget and truncation:** `matches` is cut at line boundaries within `budget_tokens`. `truncated` counts its lines.
- **"Handle of a large result":** there is no server-side handle. The handle is the cursor plus `rev`/`hash`, `total_lines` and `grep`.
  - Nothing is stored, so there is no per-session state, no expiry and no cross-account leak.
  - `requireAccess` runs on every call, including cursor pages, and the cursor binds the arguments.
  - Search, graph and `find_symbols` results are not greppable. The PR lists this under "Not covered".
- **Access matrices:** both `server/test/access-matrix.test.ts` and `lab/tests/access-matrix.test.ts` gain the `read_note` and `read_file` grep reads.
- **Manuals:** the two `mcp-tools.md` files are byte-identical (`cmp`).
- **Params described:** `targetsArg` still describes `targets` (as `Parts`). `grep` is a key inside `targets[]` (via `strictArgs`), which has no per-key descriptions, as with the existing kinds.
- **Reader budget:** the PR claims 1,999 of 2,000 tokens, with ceilings unchanged. I could not measure it myself. The `checks` job passed, which includes `mcp-tool-budget`.
- **CI:**
  - Passed: `checks`, `fails-before` (18s), `lab`, `plan`, `pr-evidence`, `attribution`, CLAssistant.
  - Pending: `bench (1)`, `bench (2)`, `bench (3)`, in run 41434826717.
  - Failing: `review-verdict/dev`, because no review has been posted for 898597d yet.
  - The PR links head bench run 41434722119 and base bench run 41434728321.
- **Fails-before:** the five new tests in `mcp-read-targets.test.ts` use `grep`, which on base is an unknown key rejected by `strictArgs`. The narrow test asserts the missing `narrow` entries. `fails-before` is green and the PR reports 5 failed and 13 passed on dev's source.
- **`--require-golds`:** I did not verify gold counts. The PR says the scripted agent never sends `grep`, so tokens should not move. The `bench` jobs, and the `bench-gate` `--require-golds` check against the base baseline, were still pending.
- **Branch drift:** the branch is behind `dev` by 1 commit (`ff95547`). I did not check whether that commit touches the reader tool text. With only 1 token of reader headroom, a rebase could tip the budget test, so a rebase is worth watching.

## Findings (blocking)
None.

## Minor
- **Hint missing on the default big read.** `largeNarrow` (the `grep` hint) is added only when the read is not answered as an outline. `read_note` and `read_file` over budget first answer their outline by default (#417), and that path keeps `outlineNarrow(...)` and carries no `grep` hint. The new test passes in CI, so it does not show whether this path lacks the hint. This is not a defect against the acceptance text.
