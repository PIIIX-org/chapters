## Findings (blocking)
1. **A single content-word match still outranks an AND match** (`server/src/search/search.ts:703-718` for symbols, `:755-760` for files; the 773f6aa stem rule is the new `isExactFile` code at `:693-707`).
   - `queryExactContext` treats every non-stopword whitespace token of a multi-word query as an "exact term". `isExactSymbol` and `isExactFile` add `EXACT_BOOST = 1` when a name, basename or stem equals any one of them. This holds even when the row came only from the vector leg and matches one term of several.
   - The MCP `search` tool and the benchmark send the whole natural-language question, so this is the default path.
   - Probe on 773f6aa:
     - **Setup:** `requestQueueRetry` (matches all three terms), `queue()`, `retry()`, `src/queue.ts` (content unrelated).
     - **Query:** `request queue retry`.
     - **`findSymbols` result:** `queue 1.0159`, `retry 1.0156`, `requestQueueRetry 0.0328`.
     - **`searchNotes` result:** `src/queue/retry.ts 1.03`, `src/queue.ts 1.016` (an unrelated file) and the symbols `queue` and `retry` all come before `requestQueueRetry`.
     - **Base order was** `requestQueueRetry`, then `queue` and `retry` (the first two lines list only the cases where the boost changes the order).
   - Stopword filtering and the generic-stem list do not fix this, because `queue`, `retry`, `search`, `config` and similar are content words.
   - This is the pattern of the #1014 regression, a name that matches one term outranking the row that matches all of them. The issue asks for exact and identifier matches to outrank fuzzy ones, not for any one-term name hit to outrank an AND hit.
   - **Fix:** restrict the boost to a whole-query match, or to a term that is itself an identifier (a compound or a quoted term) or the query's only term. Add a regression test shaped like the probe.
2. **The 773f6aa stem rule widens exactness past the PR's own spec** (`server/src/search/search.ts:703-706`). `if (ctx.termSetLower.has(stem)) return true` makes `src/queue.ts` exact for the term `queue`, as shown in finding 1. The PR text says path or basename equals a term. Only a hand-picked `GENERIC_BASE_STEMS` list is exempt, and only in multi-word queries.
3. **The new stopword test is vacuous** (`server/test/search-fusion-exact.test.ts`, test "common stopwords and generic basenames…").
   - It passes on base `search.ts` and on d5ba5b1 `search.ts`. I ran both.
   - It is wrapped in `if (indexHit)`.
   - On d5ba5b1 a stem could not match at all, so the test cannot fail for the behaviour 773f6aa added.
   - Nothing covers `STOP_WORDS`, `GENERIC_BASE_STEMS` or `multiWord`.
4. **Conflict with #1037, both textual and semantic.**

   - #1037 uses `CANDIDATES` both as the rank offset for relaxed and trigram rows ("as if after a full AND list") and as the `looksFurther` threshold.
