## Verified
- **The fix.** `blockLeg` counts the scope's blocks of every kind, capped at `EXACT_SCAN_BLOCKS + 1` (2,000+1), with an index-only scan of `blocks_container_idx`.
  - At 2,000 or fewer it orders by `cosine_distance(embedding, q)`. No index serves that, so the leg reads and sorts the scope's rows.
  - Above 2,000 it keeps `<=>` with `setHnswScan`, exactly as before.
  - It is iterative scan neither nor `ef_search`. The change matches the cause in #1035: an HNSW-unreachable node cannot be found by either setting.
  - All three vector legs (note, code file, symbol) use the helper, and no SQL other than the order expression changes.
- **Determinism.** `cosine_distance` is the function behind `<=>`, so the values are identical.
  - The exact path sorts every row in scope, so the result cannot depend on HNSW build order or on the rest of the instance.
  - I ran the #462 test plus the new deterministic test 20 times on head a70a0e5 against pg17 with pgvector 0.8.7: 20 of 20 passed.
