# Review: #1013 `fix: graph answers ordered by content, not ids (#1006)` @ 37fe72d

**Verdict: CHANGES.** There are two blockers. The core fix works: `#1010`'s `graph vault communities` case flips to pass 5/5, the PR's own test fails before the fix and passes after, and Louvain determinism still holds. But the PR breaks an existing candidates assertion, which turns CI red about 6 times in 8. And merged and `everywhere` graphs still order nodes by a random container id.

## Blockers

**1. `mcp-graph-params.test.ts` fails about 6 runs in 8 because the candidates order changed and the test wasn't updated (P1).**
- **Cause:** `server/src/graph/resolve-node.ts:60-61` (`byRank`) now puts kind before id, so `code` always comes before `note` for one path. `test/mcp-graph-params.test.ts:284-288` still builds its expected `docs/dup` candidates sorted by id (`.sort((a, b) => (a.id! < b.id! ? -1 : 1))`). It fails whenever the note's random id sorts before the file's.
- **CI:** the `checks` job on run 40216285780 is red on exactly this assertion (received `[code, note]`, expected `[note, code]`).
- **Local, on dev d20240b2 merged with the PR:** the file failed 6 of 8 runs. The PR body's "105/105" was a lucky draw. My own graph-files run also passed 105/105 once.
- **Fix:** expect `[{…kind: 'code', id: idOf['file:docs/dup']}, {…kind: 'note', id: idOf['docs/dup']}]` and drop the id sort.

**2. Merged and `everywhere` graphs still depend on random ids (P1). Acceptance asks for "a deterministic final tie-break that is NOT a random id".**
- **Cause:** `compareNodes` (`server/src/graph/assemble.ts:207-214`) breaks path+kind ties by `resourceId` (the vault or repository UUID), then node id. Two vaults or repositories sharing a path is the normal case (`index`, `README.md`, `package.json`, `src/index.ts`). This reaches node order, Louvain input, community numbers and edge order for `graph {everywhere:true}`, REST `/graph/merged` and merged `find_graph_path`.
- **Probe:** a scratch test built vaults "Alpha" and "Beta" with the same three notes in two worlds, with the vault-id order swapped. `buildGraph` gave:
  - World A: `["Alpha:index#c0","Beta:index#c1","Alpha:x#c0",…]`
  - World B: `["Beta:index#c0","Alpha:index#c1","Beta:x#c0",…]`

  The communities swap and the node and edge order differ.
- **Fix:** the PR's "Not covered" note says no content is left to decide this tie, but the container name is content. Answers already label containers by name (`edges.ts:87-88`, `in: container`), and the issue's Expected lists the container in the content key. Compare the container label (name, or `name#id8` on a collision, as `edges.ts` already does) before `resourceId`/`id` in `compareNodes`, and add a two-vault case to `graph-content-order.test.ts`.
