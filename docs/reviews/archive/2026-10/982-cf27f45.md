## Verified
- **Git and local path: the stale row goes.** The skip rule is now one function. A skipped file is pushed to `skipped` before `currentPaths.push`, so it is left out of `currentPaths`. The store's existing delete step then removes:
  - the `repository_files` row, which holds the file's content and embedding;
  - symbols (with their embeddings) and imports, through `ON DELETE CASCADE`;
  - semantic edges, through `deleteSemanticEdgesFor`.
  
  The new test checks, after the resync: `getRepositoryFile` returns null, `read_file` answers `NOT_FOUND`, and `searchNotes` and `findSymbols` no longer find the old token. All 4 cases pass (git and local path, each for "grows past 1 MB" and "gains a NUL byte").
- **A file that shrinks back is indexed again.** The same 4 tests restore the file and assert it is fully indexed after the next sync.
- **Agent push.** `POST /repositories/sync` passes the client's own `files` and `currentPaths` straight to the store. Nothing is skipped on the server, so this bug can't happen there. NUL bytes are stripped and the rest is indexed, unchanged. There is no per-file size check; the push route uses Fastify's default 1 MiB limit on the whole request body, which matches the doc. There is no push client in the repo to check.
- **NUL rule vs #969.** The two PRs agree. Git and local-path scans skip a file with a NUL byte as binary; push strips NULs. #969 keeps stripping on push through its `nulBytesAllowed: ['files.*.content']` opt-out and doesn't touch `store.ts` or `fs-scan.ts`. `git merge-tree` of #982 with #969 and with current `origin/dev` merges cleanly. The NUL check now runs on the raw bytes before decoding. That behaves the same as before, because in UTF-8 only a 0x00 byte decodes to U+0000.
- **Reporting skipped files (#465).** Not done, by owner decision D12. The scan returns `skipped: {path, reason}[]` and both callers ignore it for now. That matches the decision comment on #923 ("removed from the index" was one of the issue's two accepted outcomes).
- **A file that fails to read stays current**, as before. The new `repository-scan.test.ts` pins this, together with the exact 1 MiB boundary and an extension-less ELF blob.
- **Fails before:** with `server/src` from ff6f4ef (the tests without the fix), all 4 cases fail on `expected { …(12) } to be null`. The CI `fails-before` job shows the same 4 failures plus `repository-scan`.

## Minor (non-blocking)
- **Files that import a skipped file lose that import edge, and it doesn't come back.** I reproduced this with a scratch local-path test: `user.ts` imports `./big`, then `big.ts` grows past 1 MB and later shrinks back.
  - **What happens:** `repository_file_imports.resolved_target_file_id` is `ON DELETE CASCADE`. Deleting `big.ts` therefore deletes `user.ts`'s import row outright rather than nulling it. When `big.ts` comes back under a new id, `user.ts` is unchanged, so it isn't re-extracted. `backfillUnresolvedImports` only revisits rows that still exist, and only at boot, so it doesn't help.
  - **Observed:** `initial [{"t":"./big","r":"74d6…"}]`, then `skipped []`, then after the restore `[]`.
  - **Not new:** a real delete and re-add on the same store code gives the same result. The patch only adds a new way to trigger it.
  - **Effect on the doc:** the line "comes back on the first sync after it is indexable again" (`backend-reference.md` ~L2207–2209) is true for the file's own row, symbols and imports, but not for import edges pointing at it from other files.
  - **Suggestion:** a follow-up issue rather than more work in this PR. Make that foreign key `SET NULL` and re-resolve unresolved imports after each sync.
- The `skipped` list has no reader until #465 lands. That is intended; I note it so #465 picks it up.
