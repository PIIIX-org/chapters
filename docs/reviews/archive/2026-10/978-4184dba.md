## Findings (blocking)
1. **The first boot after the upgrade rebuilds every derived artifact, and new writes wait behind the whole backlog (P1). This fails the "no full re-extract storm on upgrade" criterion.**
   - **What happens.** 0033 leaves `extractor_version = 0` and `embedder_id = NULL` on every existing row. So `scheduleMissingExtractions` and `scheduleMissingEmbeddings` enqueue every repository file and every live note (`extraction-queue.ts:187-212`, `embedding-queue.ts:86-111`). Each file re-embeds its own vector plus up to the budget of symbols.
   - **Why new writes wait.** `claimJob` takes jobs `ORDER BY id` (`durable.ts:145`), and extraction is first-in-first-out within a repository. Every job a write enqueues after boot therefore runs after the entire catch-up backlog.
   - **Measured with the real `Xenova/bge-small-en-v1.5`** (local laptop under load, 300 notes of 2,000 chars and 60 server `.ts` files):
     - notes: **102 ms each**;
     - files: **640 ms each** (65 s per MiB, 411 symbols);
     - a note created right after boot got its vector **30.6 s later, which is the whole backlog**. With the fake embedder it also waited for the full backlog.
   - **Extrapolated:** 100k notes ≈ 2.8 h and 20k files ≈ 3.6 h of embedder time.
     - During that time new notes have no vector, so no semantic search and no semantic edges, and MCP writes report `indexed: false`.
     - Edited notes keep stale vectors.
     - A push to a large repository gets no symbols or imports until that repository's backlog drains.
   - **What the PR measured.** The PR's "20,000 files … 565.8 ms" covers only the enqueue. The docs say "search keeps answering from the old rows until each new one is written" (`backup.md`, `monitoring.md`), which is not true for anything written after boot.
   - **#980 and #981 repeat it.** Each `EXTRACTOR_VERSION` bump re-embeds everything again, because `processFile` always re-embeds the file vector and all its symbol vectors.
   - **The note re-embed is avoidable.** `git log -S` shows the note embed text (`${path}\n${JSON.stringify(frontmatter)}\n${body}`) and `Xenova/bge-small-en-v1.5` unchanged since 1f05a6f7. So any existing note vector is, apart from the old `seq` race, exactly what `Xenova/bge-small-en-v1.5+text1` produces. This last step is my inference from the history; I did not compare vectors.
   - **Suggested fix:**
     - (a) Stamp the existing note vectors with `embedder_id` instead of treating null as unknown. This can be a 0033 `UPDATE notes SET embedder_id = 'Xenova/bge-small-en-v1.5+text1' WHERE embedding IS NOT NULL` (the trigger does not bump `seq`), or a paged boot step.
     - (b) In `processFile`, reuse an existing symbol vector whose embed text is unchanged, and reuse the file vector when `extracted_hash = content_hash` and `embedder_id` matches. Then an extractor bump costs parse time, not embed time.
     - (c) Let jobs from writes go before catch-up jobs, for example a `catchUp` payload flag and `ORDER BY (payload ? 'catchUp'), id` in `claimJob`. No migration is needed for that.
     - (d) Document the real duration.
