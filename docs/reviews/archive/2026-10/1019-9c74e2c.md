# Review: #1019 `feat: unchanged-since-revision answers for reads (#682)` @ 9c74e2c

**VERDICT: CHANGES**

The design holds up. The access check runs first, notes compare `seq` and files compare their content `hash`, and the path-reuse guard looks only inside the vault. But CI is red on a test the PR breaks, and three probes I ran on head show wrong behaviour: one at the #964 base, one on files whose extraction is pending, and one on the type of `if_rev`.

## Scope and closing keyword
`Refs #682` is right. The issue's Change covers "read, search and outline calls"; this PR does read and outline and leaves search and graph to #685. The Done-when items for reads are met: the answer is under 50 tokens, any change gives full content, and there are tests with permission revocation. The argument is named `if_rev`, not `since_rev`; it is one argument, and it takes a note's `rev` or a file's `hash`.

## Contract as built
- **Answer shape:** `{"unchanged":true,"rev":N,"truncated":false}` (44 chars, about 11 tokens) or `{"unchanged":true,"hash":"<16 hex>","truncated":false}` (62 chars, about 16 tokens). The same answer comes for body, `targets` and `outline` reads. Any other value, or none, gets the full answer. `read_file` body answers now also carry `hash`.
- **#946 structuredContent:** equals the text. The read tools have no `outputSchema`, so client-side validation cannot reject the short answer.
- **#1002 targets / outline / cursor:** the check runs before any part is built, and `if_rev` is part of the cursor fingerprint. `slots` now accepts an answer with no sections when there is no cursor, and still refuses a cursor on one. One edge, not a blocker: if a file reverts to the held hash in the middle of paging, the next page gets `INVALID_ARGUMENT` "not a position of this answer" instead of `CURSOR_STALE`.
- **#1004 commit / tree:** deliberately not used, because a sync can change a file while the commit or tree stays the same. The test checks that `tree` sent as `if_rev` gets the full answer.
- **#964 last-read base:** an `unchanged` answer never calls `rememberRead`. That causes blocker 2.
- **Pending extraction:** `unchanged` ignores `index`. That causes blocker 3.
- **Account separation:** the comparison runs after `tool()`'s token, profile and scope checks and after `requireAccess` / `requireRepositoryAccess`. Revoking a vault share or a repository share gives `NOT_FOUND`, and both are tested. `pathHadOtherNote` only looks at notes in the same vault. Nothing leaks across accounts.

## Blockers
1. **CI red: `mcp-errors` expects the old parameter list.** `server/src/mcp/server.ts:1388` adds `if_rev` to `read_note`, so the unknown-argument suggestions are now `[vaultId, path, targets, outline, if_rev, budget_tokens, cursor]`. `server/test/mcp-errors.test.ts:171` still expects the list without `if_rev`. The PR's list of local test runs leaves this file out. Fix: add `'if_rev'` after `'outline'` in that expectation. (P1, confidence 1.0)

2. **An `unchanged` answer keeps an older base, so the next whole-body edit can conflict for no reason.** `server/src/mcp/server.ts:1399`. Edits with `ops`, and `append_note`, do not move the connection's base. Probe on head:
   - read gives rev 1;
   - an `ops` edit gives rev 2, and the docs say to send that `rev` back as `if_rev`;
   - `read_note` with `if_rev: "2"` answers `unchanged`;
   - a whole-body `edit_note` on top of rev 2 is merged from base rev 1 and answers **`status: conflicted`, nothing written**.

   The same sequence with a plain re-read records base 2 and answers **`applied`**. Fix: in the unchanged branch, keep the stored base only when it is already at `seq`, since that is the body the agent sent after a merge. Otherwise call `rememberRead(auth.connection.id, note.row.id, note.row.seq)`, for example after `lastRead(...)?.rev !== note.row.seq`. (P2, confidence 0.85)

3. **On a file whose extraction lagged, `unchanged` hides the outline and symbols that extraction produces later.** `server/src/mcp/server.ts:2209-2210`. Probe on head:
   - push a file, then read `targets: [{symbol: 'Pend.go'}]` before extraction runs: the answer has `index: "pending"`, `hash: c5866ba266dac086`, and the target is `NOT_FOUND` "no symbols are indexed".
   - after `flushExtraction()`, the same read with that `hash` as `if_rev` answers `{"unchanged":true,…}`.
   - without `if_rev`, it returns the symbol at lines 2-4.

   The agent is told nothing changed and never gets the part it asked for. The same applies to `outline` and the body's `symbols`, and to `index: "failed"`. Fix: compare a version that includes the extraction state. For example, do not answer `unchanged` to a hash that was served while `index` was set, by giving answers with `index` a token that differs from the plain hash. At minimum, say in `mcp-tools.md` that an answer with `index` is not something you hold. (P2, confidence 0.8)

4. **`if_rev` refuses the integer `rev` that answers give.** `server/src/mcp/read-targets.ts:294`. `ifRevArg` is `z.string()`, but `read_note` and every write answer give `rev` as an integer, and `edit_note` `base_rev` accepts both. Probe: `if_rev: 2` (a number) gets `INVALID_ARGUMENT` "expected string, received number at if_rev". Both `mcp-tools.md` copies say to send the write's `rev` as `if_rev`. Fix without adding tokens to `tools/list`: `z.coerce.string().optional()`. Its JSON Schema is still `type: string`, and the comparison is unchanged. (P2, confidence 0.6)

## Non-blocking
