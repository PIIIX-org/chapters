## Findings (blocking)
1. **`server/src/repositories/import-resolution.ts:96-100` (P2, confidence 0.6): manifest context resolves Python and Go imports to JS/TS files.**
   - `processFile` (`extraction-queue.ts:490`) and `reresolveRepositoryImports` (`'nonRelative'` scope) pass the context for every language. So a bare Python or Go specifier now goes through tsconfig `paths`/`baseUrl` and workspace package names.
   - I confirmed with a probe against the PR's `resolveImportPath`:
     - with a root tsconfig `baseUrl: "."`, `scripts/train.py` → `config` resolves to `config.ts`, and `server` to `server/index.ts`;
     - `cmd/main.go` → `utils` resolves to `utils/index.js`;
     - with a workspace package named `utils`, `ml/train.py` → `utils` resolves to `packages/utils/src/index.ts`.
   - These are false cross-language edges, and the PR body states "Python/Go import resolution is unchanged".
   - Fix: after the relative branch, apply the context only when `sourcePath` is a JS/TS source, for example `if (!/\.[cm]?[jt]sx?$/.test(sourcePath)) context = EMPTY_CONTEXT`. Add a test with a `.py` and a `.go` importer.

## Minor
- **`import-resolution.ts:107-113`:** a declared alias that fails still falls back to the `@/` convention. If tsconfig maps `@/*` to `./app/*` and the file is missing there, `@/lib/db` resolves by convention to `web/src/lib/db.ts` (confirmed by probe). This is documented as intended ("stays as a fallback"), but it conflicts with the "an alias that doesn't resolve stays unresolved" rule. Fix: use the convention only when no configured pattern matched (`!alias`).
- **`import-resolution.ts:373-374`:** the sort comparator returns 0 for configs in different directories, so it is not a consistent ordering. With `a/jsconfig.build.json`, `a/lib/tsconfig.json` and `a/tsconfig.json`, the `jsconfig.build.json` paths win (confirmed by probe), against the documented rule that `tsconfig.json`/`jsconfig.json` come first. Fix: compare `dir` first, then rank.
- **Non-workspace repos:** every named nested package.json counts as a package. In a repo with no workspace declaration, a fixture at `test/fixtures/lodash/package.json` (`name: lodash`) captures real `lodash` imports. This is tested and documented as intended (workspaces.test:116), but it is the same false-edge risk the workspace rule exists to prevent.
- **Lab:** no `fix-import-edges` check covers workspace, alias or `?raw` specifiers, and the full tier has not been run on this branch.
