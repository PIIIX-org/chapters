## Findings

1. **A long query token now breaks the whole keyword channel.** P3, confidence 0.85, `server/src/search/search.ts:22` and `:53-56`.
   - **What happens:** `lexeme()` sends every whole and part as a `$n::tsquery` parameter, so Postgres parses it when the query is bound, even inside the `CASE` in `word()`. Any lexeme over 2047 bytes fails with `word is too long in tsquery`. That needs an unbroken run of 2048+ ASCII characters, or about 683 CJK characters. MCP `search`/`find_symbols` put no length cap on the query.
   - **Probe:** `'b'.repeat(2100)` and `'a_' + 'b'.repeat(2100)` both log `[search] the keyword channel failed` and return `status: unavailable, retrieval_mode: none` with the embedder down. #1009 returns `no_match / keyword_only`, because English drops the over-long word. With the embedder up, the note keyword leg goes down too (`degraded: keyword_leg_failed`).
   - **Fix:** skip query lexemes longer than `MAX_KEYWORD_LENGTH`. The index never stores them, so they can never match. Make `lexeme()` return `''::tsquery` for them, and don't add them to `wholes`.

2. **After a rollback and roll-forward, the code keyword leg searches the previous content of files changed meanwhile.** P3, confidence 0.7, `server/drizzle/0044_identifier_keywords.sql:19-20`, `server/src/search/search.ts:69`, and the 0044 entry in `docs/self-hosting/backup.md:347`.
   - **What happens:** the index and the leg trust `keyword_fts` whenever `extracted_hash = content_hash`. Older code that extracts new content updates `extracted_hash` but leaves `keyword_fts` alone, so the stale document passes the check.
   - **Probe:** I simulated older code with a sync to new content, then `extracted_hash = content_hash, extractor_version = 4`. Searching `renamedLoader` (the new content) returned `[]`, and `parseFrontmatter` (removed) still returned `src/load.ts`. This lasts until the boot catch-up re-extracts the file; the PR measured a full re-extraction of rea at 110-132 s.
   - The backup.md entry says "Rolling forward again needs no SQL", which is wrong for these files.
   - **Fix:** gate the document on the extractor version as well, in both the index expression and `CODE_DOCUMENT` (for example `AND extractor_version >= 6`). Or document an `UPDATE repository_files SET keyword_fts = NULL WHERE extractor_version < 6` step before rolling forward.
