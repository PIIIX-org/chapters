## The byte-identical claim
**What actually changed.** Nothing about byte stability changed. I ran the PR's six byte-stability tests against dev's `server.ts` and all six already pass. The only code change is that `serverInfo.version` is now `0.2.0+<16 hex>` for each profile. The title "fix: byte-stable tool list…" says more than the diff does.

**Instructions.** `instructionsFor(profile)` depends only on the profile, so instructions really are the same for every token of a profile.

**What still varies, by design.** These variations all still come from the same code. Nothing was moved or lost, and none of it is encoded in the version:
- `tools/list` is filtered by the allow-list, the access level, the scope, and the user's live permission on the pin (`listedTools` → `livePinRank`).
- An allow-listed token gets no prompts at all (`hasPrompts = !allowedTools && profile !== 'reader'`). Its `initialize` capabilities drop `prompts`, and `prompts/list` answers -32601.

**What the version covers.** The version is the hash of the full catalog for the profile, built as an account token with admin access. It is not the hash of what a given token is sent. I ran four writer tokens against my own Postgres:

| Writer token | Tools listed | Prompts | `serverInfo.version` |
|---|---|---|---|
| Account, full | 13 | yes | `0.2.0+b1688e1bf35c20b4` |
| Allow-list of 2 tools | 2 | none (capability gone) | same |
| Account, read access | 10 | yes | same |
| Read-access vault pin | 5 | yes | same |

The PR body admits this ("deterministic subset… same version"). The docs paragraph doesn't.

## Interaction with #1011's cache key
- The PR doesn't touch `cache/key.ts`, and the definitions version is not part of `versionsKey()`.
- `cacheCaller(auth)` already carries the pin, access, profile and sorted allow-list, and the permission epoch covers changes to live permission.
- The new version can't act as a per-profile cache key for `tools/list`, because the list a token gets depends on the fields in the table above. Any cache of definitions would still need the `cacheCaller` fields plus the permission epoch.
- The PR adds no such cache, so nothing is wrong today. This is a limit on #685 and later work. [INFERENCE: future use]

## Findings

**1. Docs claim the same bytes across allow-lists and pins (P3, confidence 0.85)**
`docs/agents/backend-reference.md` lines 1997–2001 say `initialize`, `tools/list` and `prompts/list` are "the same bytes for every token of one profile, scope and access, whoever minted it, whichever vault it pins". Two cases break this:
- Allow-listed tokens: `hasPrompts` drops the prompts capability and `prompts/list`, and `tools/list` shrinks to the allowed tools.
- Pins where the user's role differs: an editor's pin hides owner-gated tools such as `update_vault` and `list_vault_shares`.

The same paragraph says the version is checked "against the served bytes". That only holds for unrestricted account tokens.

Fix: add "allow-list and the user's live permission on the pin" to the qualifiers. Say plainly that the version hashes the profile's full catalog, not what a given token is sent.

**2. Test header names a file that doesn't exist (P3, confidence 0.9)**
`server/test/mcp-cacheable-prompt.test.ts` lines 4–8 point to "(definitions-version.ts)". `definitionsVersion` lives in `server/src/mcp/server.ts`. The same comment repeats the "whichever vault it is pinned to" wording from finding 1. Fix: name `server.ts`, and qualify the claim the same way as in finding 1.
