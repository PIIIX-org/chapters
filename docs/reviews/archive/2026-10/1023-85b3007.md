## What I checked

**Creating a target re-resolves its importers, in both orders.**
- The resolver only learns about files through `has()`: `resolveFile`, `known`, and so Rust, C, C++, PHP and Ruby. Each call records `lookupKey(candidate)`, and the created or deleted path goes through the same function. So any `has(P)` call puts `lookupKey(P)` in the row's keys.
- `find` stops at the first path that exists. A row's answer can only change if a created or deleted path was among those it asked about, and those paths' keys are all recorded.
- Java and Kotlin don't use `has()`. They look up a suffix index, and the PR adds `lookupKey(`${suffix}.java`)` for each suffix it tries. For any real `.java`, `.kt` or `.kts` file whose path ends in that suffix, that key is the class name, or the directory name for `index.*`. So it matches.
- Importer first, target second: the target's key finds the row. Target first, importer second: `reresolveRequested` drops `repoSiblingsCache` before the turn, so `processFile` resolves against a fresh file list.
- If a turn uses a cache from before a concurrent sync, the rows it writes still carry the key of every path it asked about. The sync calls `scheduleImportReresolution` only after its inserts and deletes have committed (no outer transaction), and the next loop of `drainOnce` re-resolves those rows.
- Re-adding a failed request and the `for…of` loop over the Map both keep requests that arrive while it is running. `jobDrainer`'s `wanted` flag, plus polling, retry a drain that threw.

**Deleting a target nulls the importer's row instead of deleting it (#982).**
- Migration 0053 drops and re-adds the constraint under the exact name 0007 created, now `ON DELETE SET NULL`. The re-resolution then picks the next candidate or leaves the row null.
- A skipped file that is later restored comes back under a new id as a created path, so its key brings the edge back.
- The graph readers already skip null targets: `assemble.ts:597` and `neighbors.ts:180/186`.

**Every path that writes rows writes keys.**
- `syncRepositoryFiles` is the only place that inserts or deletes `repository_files`.
- `processFile` and `reresolveRepositoryImports` are the only writers of import rows, and both write sorted keys.
- The boot backfill fills keys for rows written before 0053. It runs before `listen` (`index.ts:90`), so key-based lookups never see a null-keys row written by this code.

**Cost.**
- Within one repository, a `./foo` row collapses to a single key, so the matched rows stay few. The PR body reports a Bitmap Index Scan on the 21k-row rea repository.
- [INFERENCE] The GIN index covers the whole instance, while the repository filter is applied through the join. A common key (`index` directories, `src`, unresolved Java `List`/`util`) or a large first sync could make the bitmap scan read rows from every repository. Only a single-repository instance was measured.
- On the first boot, computing keys takes time proportional to all import rows and holds up `listen`. The PR documents this (336 ms for 21k rows).

**Interaction with #987's manifest context.**
- Non-JS importers still get `EMPTY_CONTEXT`.
- Relative rows don't depend on the context, so the `nonRelative` pass after a manifest change recomputes keys for exactly the rows the context can change.
- Both passes share one `getRepoSiblings` load after the cache is dropped.
