## Findings (blocking)
1. **`.github/workflows/ci.yml` (migration step) and `.github/scripts/migration-order-check.mjs`:** the guard breaks every dev→prod promotion that carries a migration.
   - `pull_request:` in `ci.yml` has no branch filter, so `checks` also runs on PRs to `prod` (required there too, #574). The step then uses `--base <prod tip> --head <merge of dev into prod>` against `origin dev`.
   - Every entry the promotion adds already exists on dev, and the newest one equals dev's newest.
   - I ran `--base <real prod tip d3b210e> --head origin/dev --dev origin/dev`. It exits 1 with 23 "added" entries and three errors each: "already exists on dev", "`when` not greater than dev's newest", and "`idx` not greater than dev's largest".
   - The PR's own evidence only covers the case where `--dev` equals the base. It never tests a promotion.
   - Fix: run the step only when the PR base is `dev` (or on `merge_group`), or skip dev-sourced entries when the base is `prod`.

## Minor (non-blocking)
- **Merge-group forwarder does not check the PR head against the queue commit.**
  - `merge-group-forward.mjs` reads the live `GET /pulls/N` head sha and the latest check run on that sha.
  - It never compares that sha with the PR head inside the queue commit (`HEAD^2`, or the merge group's head commit). A push after enqueue would forward a result computed for different content.
  - GitHub normally dequeues a PR on a new push, and `checks` is re-run for real on the queue commit. So I rate the exposure low, but the equality check you asked about is not implemented. A cheap guard would compare `pr.head.sha` with `git rev-parse HEAD^2` when `HEAD` is a merge commit.
- **No wait or poll when the PR-level check is in progress.**
  - `forward()` fails immediately with "still in_progress", and `fails-before` is a required status, so that ejects the entry.
  - `fails-before` and `attribution` re-run on `edited`, `labeled`, `unlabeled` and `ready_for_review` (cancel-in-progress is on). So a body or label edit during the roughly 25s run window right after enqueue ejects the entry.
  - The fail-with-"re-queue" message is documented and deliberate. A short poll (for example up to 2–3 min) would remove the race.
- **Other required checks have no `merge_group` trigger.**
  - Branch protection on `dev` requires `checks`, `pr-evidence`, `fails-before`, `plan`, `lab`, `bench-gate` and `review-verdict/dev`. The ruleset requires only `checks`. No merge queue rule is active yet.
  - Once the queue is enabled, any of those other contexts without a `merge_group` trigger would never report on queue commits. The PR body doesn't list this under "Not covered".
- **Vacuous rule and renames.**
  - The diff uses `--no-renames`, so a renamed or moved test file counts as added (`A`). If it passes on base, a `fix:` PR fails unless the file gets an exempt marker.
  - The docs mention characterisation tests but not renames. A one-line doc note would do.
- **Perf margin.** Alone on the runner, p95 was 194 ms against the 250 ms limit (max 796 ms). The test is much steadier than under suite load but not immune.
- **Silent exit under a symlinked path.**
  - `migration-order-check.mjs` uses the repo's usual `import.meta.url === pathToFileURL(argv[1])` guard.
  - On macOS under a symlinked path (`/tmp` → `/private/tmp`) it ran nothing and exited 0, which is a fail-open for local runs. I hit this myself.
  - Linux runners aren't affected. Every script in the repo has the same guard, so this is pre-existing and not caused by this PR.
- **Unexercised paths.** The `merge_group` runner path, the fails-before runtime path for the vacuous rule, and the real `merge_group` event have not run. This is acknowledged in the PR's "Not covered" section.
