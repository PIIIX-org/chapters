## Findings (blocking)
1. **A local folder records a commit while the index holds files that aren't in that commit.** `server/src/repositories/scheduler.ts:115-126` (and the matching claim in `docs/agents/backend-reference.md:2450`). `cleanWorkTreeCommit` treats an empty `git status --porcelain -- .` as "the indexed files are HEAD". `git status`, however, hides untracked files matched by ignore rules that `GitignoreRules(root)` never reads:
   - the parent `.gitignore` files and top-level `.git/info/exclude` when the folder is a subdirectory of a work tree (the code supports that case through `--is-inside-work-tree` and `-- .`);
   - `core.excludesFile`, including the default global ignore.

   Probe results:
   - **Subfolder case.** The repository root's `.gitignore` says `dist/`, and `packages/app` is connected with an untracked `dist/out.js`. The result is `commit = HEAD`, while the index is `["dist/out.js","src/a.ts"]` and `git ls-files` lists only `packages/app/src/a.ts`.
   - **`core.excludesFile` case.** An untracked `secret.env` ignored through `core.excludesFile` is indexed under `commit = HEAD`.

   So the answer names a commit that does not describe what the agent reads. The code comment "Untracked files the folder's ignore rules let through … count as changes, as in `git status`" is wrong for these rule sources.

   Fix: after the scan, also require that no indexed path is untracked. For example, run `git ls-files --others -z -- .` (without `--exclude-standard`, so ignored files are listed too) and return null if it intersects `currentPaths`. Alternatively, check `currentPaths` against `git ls-files -z -- .`. Add a test for each case.
2. **Answers name the new commit for symbols and vectors that still come from the old content.** `skills/elara/references/mcp-tools.md:45` (identical in `skills/chapters/…:45`), `docs/agents/backend-reference.md:2438`, and the answers at `server/src/mcp/server.ts:2117,2153`. The docs say the version is "the version its index was built from". The code writes `commit`/`tree` in `syncRepositoryFiles`, before extraction runs.

   Probe (extraction held on a gate after a push of commit B over commit A):
   - `repository_status` shows `commit: "bbbb…"` with `filesPendingExtraction: 1`;
   - `find_symbols alphaOrbit` returns `commit: "bbbb…"` and the symbol `alphaOrbit` at line 1, with A's snippet;
   - `read_file` returns `commit: "bbbb…"`, B's content (line 1 is `// moved`), and the outline `[{name: "alphaOrbit", startLine: 1}]`;
   - `search` gives the same result as `find_symbols`.

   `search` and `find_symbols` heads do carry `index.pending_files`, but `read_file` has no such signal, and the docs promise more than the code delivers.

   Fix: state in both `mcp-tools.md` copies and in `backend-reference.md` that `commit`/`tree` name the stored file contents, and that symbols, outlines and embeddings follow once `filesPendingExtraction` is 0 (`index.pending_files` absent). Optionally, add that pending signal to `read_file`'s head.
