## Numbered blockers

**1. Over-long query token takes down the keyword channel: fixed.**
- In `search.ts`, `lexeme()` now returns `''::tsquery` for any lexeme longer than `MAX_KEYWORD_LENGTH`. `MAX_KEYWORD_LENGTH` is 200, and `identifiers.ts:67` already drops longer lexemes on the stored side. Such a lexeme is also left out of `wholes`. 200 UTF-16 units is at most 600 bytes in UTF-8, well under Postgres's 2,047-byte word limit.
- **Fails before:** with 2a55cb3's `search.ts` in a tree I built from CI's merge ref `03b4dee`, `a query token too long for a tsquery word leaves the keyword leg answering` fails. Postgres raises `word is too long in tsquery` and the test gets `expected 'none' to be 'keyword_only'`. With head's `search.ts` it passes. Head runs search-identifier-keywords 14/14, search-identifiers 19/19 and migration-order 2/2.
- **Named probe**, run as a scratch test (since deleted) through `findSymbols` and `searchNotes`:

  | query | embedder down | embedder up |
  |---|---|---|
  | `'b'.repeat(2100)` | `no_match`, `keyword_only` | `no_match`, `hybrid` |
  | `'a_'+'b'.repeat(2100)` | `no_match`, `keyword_only` | `ok`, from the vector leg |
  | `'中'.repeat(700)` | `no_match` | `no_match` |

  No probe reported `keyword_leg_failed` or `unavailable`.
- **Accepted behaviour:** an over-long part drops out of the AND rather than matching nothing, so `x.<2100 b>` matches by `x`. The test states this on purpose, and it matches how `websearch_to_tsquery` already skips long words on the base.
- **Index still used:** `EXPLAIN` with `enable_seqscan=off` shows a `Bitmap Index Scan on repository_files_keyword_idx` for the leg's expression now that it has the `extractor_version` condition.
