# Review of PIIIX-org/chapters#1081 — feat: repositories of one account share vectors by embed key, equal contents are parsed once
Head reviewed: 382f8e20a073558bcbe7525d3a476c8522d65d58

I read the diff and the surrounding code. I did not run tests. CI on this head is still pending, and the bench pair is still running on the pre-renumber commit.

## Scope checked
Everything listed in the assignment: account separation, correctness and invalidation, migration 0064, the extraction-queue bench and golds, and the #684 acceptance. The PR adds no MCP tool or read surface, so the access matrix, `mcp-tool-budget` (the 2,500 reader ceiling) and the manuals don't apply. The PR's own delta there is 0. The #1077+#1078+#1079+#1080 combined delta against 2,500 is outside this PR and I did not compute it.

## Verified
- **Account separation**
  - `vectorsInAccount` restricts the rows to `r.owner_id = (SELECT owner_id FROM repositories WHERE id = <repo>)`. Another account's rows never match.
  - The result is the vector for text the caller already holds, so no content comes back.
  - A repository shared to other users keeps its single `owner_id`, so sharing adds no cross-account path.
  - `embedKey` is `sha256(EMBEDDER_ID \n text)[0:16]`. A changed embedder changes every key, so old vectors are never matched.
  - The parse cache is process-local and holds only symbols, imports and sites. It stores no vectors and no content, and its key is `EXTRACTOR_VERSION:language:grammar:contentHash`.
- **Parse cache key**
  - Its grammar tag (`.tsx` → tsx, `.h` → h) matches what `extractStructure` picks (`typescript`+`.tsx` → tsx, `c`+`.h` → cpp).
  - `contentHash` is `sha256(cleanContent)` from `store.ts`.
  - The cached result is returned by reference, but `codeBlocks` takes `readonly ExtractedSymbol[]`, and I found no mutation of symbols, imports or sites in `code-blocks.ts`, `code-edge-rules.ts` or `code-edges.ts`.
  - The cache is in-process, so an `EXTRACTOR_VERSION` bump arrives with a redeploy, and the version is also in the key.
- **Deletes and orphans**
  - Vectors are copied into the new rows, not referenced. Deleting repository A cascades only its own blocks and cannot orphan or wrongly delete B's vectors.
  - Equal content gives identical blocks, because the code blocks are built from the same symbols and `embedText`, and the test compares embed keys and vectors for equality.
  - `newKeys` and `changed` now count vectors taken from another repository as new to the file, which keeps the #1007 semantic edge refresh correct.
- **Migration 0064**
  - It is journal idx 64 with `when` 1793800000000. That is above dev's 0062 (1793700000000) and above #1077's 0063 (idx 63, 1793750000000), so with #1077 landing first the journal is contiguous.
  - The index matches the schema.ts definition and the query predicate (`owner_type='code' AND embedding IS NOT NULL`), so the planner can use it.
  - If 0064 lands before #1077, #1077 must renumber to a `when` above 1793800000000 (and take a later number). Otherwise an instance that already applied 0064 skips 0063 for good, which is the #501 failure mode.
- **Fails-before**
  - Two of the three `blob-sharing.test.ts` tests fail on an assertion on dev: the second repository embeds every text, so `expect(second).toEqual([])` and the "only its own new texts" check both fail.
  - The third test, "another account embeds the same files itself", already passes on dev. It is a negative control.

## Findings (blocking)
1. `docs/self-hosting/backup.md` — no entry for migration 0064.
   - Every recent migration has a "Migration 00NN (…)" entry stating whether it is additive and whether older code runs on it with no SQL. 0060, 0061 and 0062 do, and #1077 adds one for 0063.
   - 0064 adds a plain `CREATE INDEX` on `blocks`, with no data rewrite. Add a one-line additive entry: older code runs on it with no SQL, and the index only adds a little to code block writes.
   - The same entry should say that a plain `CREATE INDEX` takes a SHARE lock on `blocks` at boot, so on a large table writes to `blocks` (extraction, note embeds) wait while the index builds. There is no `CONCURRENTLY` because the drizzle migration runs in a transaction. This matches the 0061 `blocks_symbol_name_idx` precedent.

2. `server/test/blob-parse-cache.test.ts`
   - On base this file fails because `blob-cache.js` does not exist (module not found), not on an assertion.
   - The PR body only claims fails-before for `blob-sharing.test.ts`, so the rule is met through that file.
   - Nothing asserts through `processFile` that a second repository's file is not parsed again. The body's "0 parses, 150 reused" figure is a manual measurement. Add an assertion on `parseCacheStats` in `blob-sharing.test.ts` test 1 (parsed unchanged after repository B syncs), which would also fail on base.

## Minor
- `embedText` includes the path (`${path}\n${content}`, and `symbol … in ${path}`). Identical content at a different path in the second repository therefore gets a different key and is embedded again. Sharing works for the same path (clone, branch, fork) but not for a moved or renamed file. This narrows the #684 "identical files across repositories" acceptance and is not stated in the PR.
- The partial index is on `embed_key` alone and spans all accounts. For widely duplicated boilerplate (a LICENSE file, say) `vectorsInAccount` reads every account's matching rows before the `owner_id` join filters them. Cost grows with global duplicates, not with the account's own data. If it matters, narrow the index to `(embed_key, container_id)`.

## Evidence not yet available
- **CI on head 382f8e2**: `checks`, `fails-before`, `evaluate` and the others are pending or cancelled from earlier runs.
- **Bench / all-suite with `--require-golds`**: the same-base pair is head run 41445753788, on 9a27fed (the commit before the renumber), and base run 41445759897, on ff95547. The head run was `in_progress` and the base run `queued` when I checked, and bench (1–3) has no result for either. The PR touches `extraction-queue.ts`, so merge needs those results with identical rankings and no gold lost, plus a rerun on 382f8e2 or a statement that the renumber-only delta (journal, SQL, schema.ts) can't change them. Recheck before merging.

Verdict: CHANGES — add the backup.md entry for 0064 and fill in the evidence gaps above. Nothing found leaks across accounts or deletes shared vectors.
